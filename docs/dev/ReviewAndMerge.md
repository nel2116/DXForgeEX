# Review, merge and cleanup

<!-- last-reviewed: 2026-11-07 -->

How a PR gets from "done" to merged into `develop`, and how local worktrees are cleaned up afterwards. The rules to follow are summarized in the root `AGENTS.md`; this file has the mechanics and the verified pitfalls.

## Cross-model review with Codex (`CodexReview.ps1`, issue #56)

Before a PR is proposed for merge, run `./CodexReview.ps1 -Pr <N> -Post`. It checks out the PR head into a throwaway worktree under `%TEMP%`, runs `codex review` against the tip of the PR's base branch (both fetched from the repo `gh` resolves into script-private `refs/codex-review/<N>-<runId>/*` refs, deleted afterwards, so `origin` layout does not matter), and posts the result as a PR comment (omit `-Post` to only print it). Codex reads the root `AGENTS.md` of the checked-out PR head, so the project rules there apply to its review.

The point is a reviewer that does not share the author's blind spots: on its first run it found a P2 in PR #52 that both the implementing worker and the coordinator's diff read had missed (the editor never calls `script::update()`, so the `begin_play` pending queue grows on every game-DLL reload).

In orchestrated work the **implementing worker** runs `-Post` once CI is green, checks each finding, and either fixes it or replies on the PR with why not, then re-runs the review (issue #195: the coordinator's turns are the expensive ones, because its context is large). After a PASS it sends 「PR 準備完了」 with `ask`, listing any finding it did not fix; **the coordinator verifies those**. `-SetStatus` is coordinator-only.

`-Post` ends every PASS/FINDINGS comment with `<!-- codex-review verdict=<pass|findings> sha=<40 hex> base=<branch> -->` (none for merged PRs or an UNKNOWN verdict). Only the last line of a comment that starts with `## Codex レビュー` and was written by the logged-in `gh` user counts, so another person's comment or a marker quoted in a review does not. `-SetStatus` skips Codex when the last marker for the current head and base says pass (a later FINDINGS on the same head wins) and that head's `codex-review` status is neither `failure` nor unreadable (a review without `-Post` leaves only the status, and an older PASS must not overwrite it); the protection check still runs first, and `-ForceReview` reviews anyway. `-Post` also prints how many FINDINGS the PR has had, and past 3 tells the worker to consult the coordinator (comments from before these markers are not counted). Test: `pwsh -NoProfile -File Tests/CodexReview.Tests.ps1` (fake `gh`/`codex` first on `PATH`).

Verified pitfalls:

1. On Windows, Codex's sandbox is disabled by default, and then even a read-only review has every shell command rejected as `blocked by policy` — Codex then reports it could not read the diff instead of reviewing. The script passes `-c windows.sandbox="unelevated"` per call (the global `~/.codex/config.toml` is untouched) and fails loudly if `blocked by policy` still appears.
2. `codex review` rejects `--base` combined with custom instructions, so the diff range is named inside the prompt.

Expect 1–2 minutes per PR; it neither builds nor tests, so it complements CI rather than replacing it. Already-merged PRs work too (issue #58): the base tip already contains the PR, so the script instead diffs the merge commit's two parents and has Codex label each finding "still present" or "fixed since" against the current base tip — merge-commit merges only (every PR so far). Several reviews can run in parallel (fetch uses `--no-write-fetch-head` because the shared `FETCH_HEAD` otherwise races). A killed review leaves its worktree and refs; `CleanupMerged.ps1` removes them once the run's lock is free (see "Local cleanup").

## Auto-merge into `develop`

Branch protection on `develop` requires five checks — the three CI jobs, `No hold label` (`.github/workflows/pr-automation.yml`), and the commit status `codex-review` — with admins included, so nothing (not even an admin `gh pr merge`) lands without them.

- The coordinator runs `./CodexReview.ps1 -Pr <N> -Post -SetStatus` **only once the PR's completion criteria are met** (CI green, GUI checks done, earlier findings resolved). With the worker's PASS on the head it costs no second review.
- The human-approval gate (issue #160, the next four points) is **off** since 2026/11/03: this is a solo project and the user prefers speed, so `-SetStatus` merges as soon as CI and `codex-review` pass, and the coordinator runs it itself. The `Merge approved` job runs only when the repository variable `REQUIRE_MERGE_APPROVAL` is `true`. To turn the gate on, set that variable **and** add `Merge approved` to the required checks; a required job that is skipped counts as passed, so the protection alone does nothing. `-SetStatus` then reports "awaiting approval".
- When the gate is on, recording the review and approving the merge are separate. `-SetStatus` records the verdict and schedules the auto-merge, but the PR only merges once a **human** adds the `merge-ok` label, which turns `Merge approved` green. Before #160 nothing in the gate needed a human, so an agent could review and merge on its own; Claude Code's auto mode blocked that as "Merge Without Review" on 2026/11/02, but not consistently. Agents report "awaiting approval" instead and never add the label. They act through the user's own `gh` account, so GitHub cannot tell them apart; the PreToolUse hook `Tests/guard_merge_approval.py` (tests: `Tests/guard_merge_approval_test.py`, run in CI) blocks `gh` commands that add `merge-ok`. It is a guard rail against mistakes, not a security boundary: it does not see commands hidden in a script file or `curl`.
- The approval belongs to a head, like the status. `Merge approved` passes only if the last time `merge-ok` was added (issue events) is later than the time the head was pushed. The push time is when the head last became that SHA: of this PR's `pull_request` workflow runs in time order, the first of the trailing run of that SHA. So an approval given before a push never counts, even if the label is still there, and neither does one given to B when the head is force-pushed back from B to an earlier A (taking the *first* run of the SHA let it count; found by Codex on PR #161). A push (`synchronize`) also removes the label, so it is clear that a new approval is needed; removing it is only a convenience. Re-running an old `synchronize` run removes the label again, which only errs on the safe side.
- PRs from forks cannot be approved this way (their runs have no `pull_requests` entry, and their token cannot remove the label), so `Merge approved` fails for them; push the branch to this repository instead (found by Codex on PR #161).
- Limitation (same for `No hold label`): `pull_request` runs the PR head's copy of the workflow, so a PR that edits `pr-automation.yml` could fake the check. Such a change is visible to the Codex review and to whoever approves.
- Rollout order: `Merge approved` became required only after PR #160's workflow was on `develop`; requiring it earlier would block every open PR whose branch lacks the job (those need `develop` merged in first).
- The verdict is read from `codex review`'s own output format — every finding is rendered as a `- [P0..P3] title — file:lines` line under `Full review comments:` — because `codex review` ignores custom instructions about output format (a requested `VERDICT:` line never appeared; found by Codex itself on PR #96). Any finding, regardless of severity → `codex-review` = failure.
- Success (on the reviewed SHA, followed by `gh pr merge --auto --merge`) needs positive evidence too: no finding line **and** the phrase 「問題は見つかりませんでした」, which the prompt asks for and which free-text summaries do honor; anything else (e.g. `Reviewer failed to output a response.`) → failure, so an incomplete review never passes.
- If a Codex upgrade changes that rendering, a review with findings would read as PASS, so re-check the format after upgrading `codex-cli` (verified on 0.163.0).
- `-SetStatus` refuses (before reviewing) unless the base branch's protection requires `codex-review` and `No hold label` (and says it awaits approval when `Merge approved` is required too), and re-reads the PR's base before scheduling the merge, since a base changed mid-review would bypass the protection check.
- A status belongs to a commit, so pushing a fix drops it and the PR waits for a fresh review — no unreviewed fix can merge.
- A human stops a merge by adding the `hold` label (also works after `codex-review` passed); removing it re-runs the gate.
- GitHub deletes the head branch on merge (`delete_branch_on_merge`), and the `close-issues` job closes `Closes #NN` issues, which GitHub itself only does for PRs into the default branch (`main`). It runs on `push` to `develop` and looks up the merged PR from the pushed commits (`commits/<sha>/pulls`), because both obvious triggers fail: a fork PR's `pull_request` token is read-only, and `pull_request_target` always runs the *default branch's* (`main`'s) copy of the workflow, so a workflow that exists only on `develop` never fires (both found by Codex on PR #96).
- Pitfall: `gh pr merge --auto` merges *immediately* when no required check is pending, so never use it on a branch without this protection.

## Hooks that keep the flow (`Tests/guard_review_flow.py`, issue #195)

- **`-SetStatus` in a worker conversation is blocked.** A worker is recognised by the first user message of `transcript_path` starting with Orca's `worker-start` preamble (`You are a dispatched worker.`). Environment variables cannot tell: `ORCA_TERMINAL_HANDLE` is `structworker_…` for structured-mode workers, but PTY-mode workers have `term_…` like the coordinator, and the mode follows a user setting. On 2026/11/05 this classified 68 of 72 local worktree conversations as workers and 3 of 44 root conversations. When the transcript cannot be read or has no preamble, nothing is blocked, so a coordinator is never stopped; a resumed conversation that lost its first message is not recognised. Like the merge-approval guard it does not parse the shell: `CodexReview` plus `-SetStatus` (or a PowerShell prefix such as `-SetS`) anywhere in one command blocks, so pass commit messages and PR bodies that mention them with `-F`/`--body-file`. `orca orchestration` commands are the exception, since `ask` has no file option: quoted text containing whitespace and here-docs are ignored there, while a real call next to them still blocks. A script file or splatting is not seen; it is a guard rail, not a boundary.
- **`gh pr create` needs a stamp.** `./PrePr.ps1` picks the steps from the diff against `origin/develop` (table in `Get-PrePrPlan`; `check_conventions.py` always, documents and skills build nothing), refuses uncommitted tracked changes, prints one line per passing step and the tail of the first failure, and on success writes HEAD's sha to `git rev-parse --git-path dxforge-prepr-stamp` (per worktree). The hook compares it with HEAD in the tool call's `cwd`; a `cd` inside the same command is not seen, and outside a git repository nothing is blocked. The stamp cannot prove the printed self-check items were read, so they go in a 「自己点検」 section of the PR body. Test: `pwsh -NoProfile -File Tests/PrePr.Tests.ps1`, `python Tests/guard_review_flow_test.py`.
- **Context size warning** (`Tests/context_size_warning.py`, PostToolUse): reads only the last 256 KiB of the transcript, sums the last assistant message's `input + cache_read + cache_creation`, and over `DXFORGE_CONTEXT_WARN_TOKENS` (default 120000, `0` disables) adds a note via `additionalContext`, then again each time the context grows by `DXFORGE_CONTEXT_WARN_STEP` (default 50000; `0` or less warns once) (#256). Each stage warned creates its own mark `<session>-<stage>` under `%TEMP%\dxforge-context-warning\` with `O_EXCL`, so parallel tool calls warn once per stage. It never blocks.
- **Large read guard** (`Tests/guard_large_read.py`, PreToolUse on `Read`, #256): blocks a `Read` without `offset`/`limit` of a text file over 600 lines or 30 KB, and of any `.jsonl` transcript (use `Tests/usage_report.py`). Images, PDFs and notebooks pass. Passing `limit` is the way to read a whole file on purpose.
- **Coordinator waiting** (#256): wait for workers with `orca orchestration check --wait --timeout-ms 3600000 ...` run through `run_in_background`, not in the foreground. A foreground Bash returns after 10 minutes, and every wake-up re-reads the whole context. Read `orca skills get orchestration` once per conversation; afterwards grep it for the part you need.

## Orchestration helpers (issue #195)

- `./StartWorker.ps1 -SpecFile <file> -Name <worktree> [-Size small] [-Run <id>]` concatenates `docs/dev/WorkerRules.md` and the spec for `worker-start`; `small` adds `--model claude-sonnet-5-5`. New worktrees start from `-BaseBranch` (default `origin/develop`): without `--base-branch` Orca uses the repository default, `main`, and the worker's first check fails. To retry a failed Task use `-Task <task> -RetryOf <dispatch> -Worktree path:<path>` without a spec, because Orca's `--retry-of` needs `--task` and does not inherit the placement.
- `./.claude/skills/gui-check/start-gui-check.ps1 -Pr <N> [-Size normal] [-Run <id>] [-DryRun]` hands a PR's GUI check to a new worker: it reads the numbered steps under the `## GUI の確認手順` heading of the PR body (exit 3 if there are none, 2 if the PR is not open, 4 while another `gui-check-pr-*` worktree exists, because mouse and key input act on the whole desktop), joins them to `worker-spec.md`, and calls `StartWorker.ps1` with a new worktree `gui-check-pr-<N>` based on `origin/develop` and the small model. The worker fetches `refs/pull/<N>/head`, checks that it matches the head read at start, checks it out detached, builds, checks, puts images in the PR body with `push-pr-assets.ps1`, deletes its projects, and returns only one line per step in `worker_done`. Before merging, compare its `head:` line with the current PR head; if the PR moved after the check, run it again, because neither CI nor `CodexReview.ps1` knows which head was checked on screen. `CleanupMerged.ps1` does not remove that worktree because its branch has no PR; after `worker-release`, run the same script with `-Cleanup` (`orca worktree rm --delete-branch`, no `--force`).
- **Reading GUI check images in a coordinator conversation is blocked** (`Tests/guard_gui_images.py`, `PreToolUse` on `Read`): an image in a `gui*` folder under `%TEMP%`, in a conversation that is not a worker and that has used the `orchestration` skill or started a worker (assistant `tool_use` records in `transcript_path`). When it cannot tell (unreadable transcript, no such record), nothing is blocked, so a plain conversation can still look at images. Test: `python Tests/guard_gui_images_test.py`.
- `./WorkerStatus.ps1 [-Run <id>] [-Json]` reads `status.terminal`/`status.liveness` from `worker-read --json` for each unreleased worker, because `worker-show`'s `state: ready` and `worker-list`'s `liveness` (`unverifiable` for structured workers) stay the same after the process ends and `send` still returns `ok` (2026/11/05: three workers dead for about 11 hours). Check it after limits or long silences. Test: `pwsh -NoProfile -File Tests/WorkerTools.Tests.ps1`.
- `python Tests/usage_report.py [--since YYYY-MM-DD] [--until ...] [--project <text>] [--session <text>] [--top N] [--json]` summarises turns, cache reads, per-turn reads, output and images per conversation from `~/.claude/projects` (read-only).

## Local cleanup (`CleanupMerged.ps1`)

`./CleanupMerged.ps1` (`-DryRun` to preview) removes a worktree/local branch only if its PR is merged, its tip is contained in `origin/develop`, and the worktree has no changes or untracked files (so a freshly created, still-empty worker worktree is never touched), then fast-forwards the root `develop`. Run it without being asked after merges and in the pre-flight check of an orchestration.

- `orca worktree rm` can return success before Orca has finished deleting the branch/folder (issue #104: the following `git branch -D` failed with `used by worktree`), so after it the script polls every 0.5 s for up to 15 s until the worktree registration, `refs/heads/<branch>` and the folder are all gone; a branch still left is deleted with `git branch -D`, a registration still left gets a warning and its branch is not touched. The local-branch pass re-reads `git worktree list` instead of trusting what the worktree pass removed.
- It also keeps a worktree in which an Orca terminal is open (issue #133: `orca worktree rm` closes the worktree's terminals, so running the script right after a merge killed a worker before its `worker_done`, and the Dispatch ended `failed`). It checks `orca terminal list --json` (every live PTY terminal with its `worktreePath`). If Orca is installed but the list cannot be read or is truncated, it keeps the worktree too.
- `orca terminal list` does not show workers started in Orca's **structured** mode (`worker-start` receipt `"mode":"structured"`, handle `structworker_…`; the mode follows the user's new-agent-tab setting), so on 2026/11/03 the #133 guard let the script delete a live worker's worktree again (issue #166). It therefore also reads every Run (`orchestration run-list`, following `nextCursor`) and each Run's `orchestration worker-list --run <id>` (without `--run` it only covers the caller's bound Run), and keeps a worktree that is the `workspace` (`<repoId>::<path>`) of any worker whose `terminalState` is not `released`. If either list cannot be read, it keeps the worktree. The lists are read once per run and only when a worktree is otherwise removable (27 Runs / 66 workers took ~11 s on 11/03). Stale `retained` workers of long-gone worktrees only matter if the same path is reused. A worker's worktree is therefore removed by the first run after `worker_done` + `worker-release`, whatever order the coordinator uses.
- If the folder survives (a process holds a DLL from it — on 10/27 a pwsh stuck in a Debug assert dialog), it warns and lists processes whose `Get-Process` `Modules` lie under the folder (name + PID); it never kills them or deletes the folder, and cannot see 32-bit processes' DLLs, non-DLL file handles, or processes it lacks rights to. `-DryRun` neither waits nor scans.
- It also removes what a killed `CodexReview.ps1` left (issue #183: a review stopped with `TaskStop` is killed without running its `finally`, so PR #212's `refs/codex-review/212-f58bae6e/*` and log stayed). The review holds `%TEMP%\DXForgeCodexReview-<PR>-<runId>.lock` from before its first ref until its worktree is gone, opened with `FileShare.None | Inheritable` so that `codex` and its children keep it after the script dies. The `== review worktree` section goes run by run over registered `DXForgeCodexReview-*` worktrees (detached only), `refs/codex-review/*` and the lock files: if the lock opens, nobody is using the run, and it removes the worktree with `--force`, the folder, refs, log and lock; on a sharing violation it leaves everything; with no lock, or one it cannot check (a review started by an older script has none), it deletes nothing, warns and prints the manual commands. `%TEMP%` is shared between clones, so the lock holds the repository's git common dir, and a lock with no worktree or ref in this repository is removed only when that matches (removing another clone's would leave its registration and refs with nothing to recover them). `git worktree remove` drops the registration even when it cannot delete the folder, so a free lock also covers an unregistered folder; if something cannot be removed, the lock stays and the next run retries. The log of a failed review whose worktree was removed normally has no lock and is kept, because the error message points to it.
- Test: `pwsh -NoProfile -File Tests/CleanupMerged.Tests.ps1` (~1 min; disposable repos under `%TEMP%`, fake `gh.ps1`/`orca.ps1` put first on `PATH` and verified via `Get-Command` before each run, so the real GitHub/Orca are never called; `-ScriptPath` runs it against another copy, e.g. the pre-fix script, `-Case` picks cases); CI runs it in the `Editor build` job.
