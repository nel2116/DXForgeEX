# Architecture

Reference for agents and contributors. The short version is in the root `AGENTS.md`; this file is the detail it points to.

## Renderer status

Current implementation has PBR direct lighting (GGX/Smith/Schlick BRDF in `Shaders/BRDF.hlsli`) plus Image-Based Lighting (Primal Day 075, issues #35–#37). The IBL maps are baked offline by `ContentTools` (`EnvMapProcessing.*`/`EnvMapProcessing.hlsl`: equirectangular → cubemap, diffuse irradiance prefilter, specular prefilter with one mip per roughness step, BRDF integration LUT; exposed to the editor as `PrefilterDiffuseIBL`/`PrefilterSpecularIBL`/`ComputeBrdfIntegrationLut`). At run time they are bound through an `ambient` light (`graphics::light::ambient`, `ambient_params` in `Renderer.h`, one per light set, carried to shaders as `GlobalData.AmbientLight`); the material pixel shaders (`EngineTest/TestShader.hlsl`, the editor's `Resources/MaterialEditor/DefaultMaterialShaders.hlsl`) evaluate it, and `PostProcess.hlsl` draws the specular cubemap as the sky. `EngineTest` loads the maps from `x64/ibl/*.texture` and falls back to direct light only when they are missing. For "what comes next" on the renderer, follow Primal's history rather than assuming a fixed milestone.

## Projects

`DXForge.sln` has 4 solution configurations, all `x64`: `Debug`, `DebugEditor`, `Release`, `ReleaseEditor`. The `*Editor` configs build the engine as the `DXForgeEngineDLL` dynamic library for use by the editor; the plain `Debug`/`Release` configs build `EngineTest` as a standalone native executable that exercises the engine without the editor.

- **DXForgeEngine** (`StaticLibrary`) — the engine core. Linked into both `EngineTest` and `DXForgeEngineDLL`.
- **DXForgeEngineDLL** (`DynamicLibrary`) — thin C-ABI wrapper (`dllmain.cpp`, `EngineAPI.cpp`, `EntityAPI.cpp`) exposing `DXForgeEngine` to the C# editor via `DllWrappers`; also hosts `ShaderCompilation.cpp` (DXC), which `EngineTest` compiles in as well (Primal Day 076). `CreateResource`/`DestroyResource` (Primal Day 077, issue #30) create engine resources (mesh, texture, material) from the editor assets' `PackForEngine()` bytes; the logic lives in `ResourceUpload.cpp`, which `EngineUnitTests` compiles in and exercises (`Tests_ResourceUpload.cpp` without a GPU, and the `--render` WARP run, which builds its scene through it). The material bytes are `u32 texture_count, id texture_ids[], material_init_info` packed without padding (see `ResourceUpload.h`). `InitializeEngine`/`ShutdownEngine` (Primal Day 078, issue #31) compile the engine shaders and initialize Direct3D 12, through `EngineInit.cpp` (`editor::initialize_engine`/`shutdown_engine`), which `EngineUnitTests` compiles in: `Tests_EngineInit.cpp` covers the failures that need no GPU, and the `--render` WARP run initializes, creates/destroys resources, and shuts down through it. Unlike Primal, the DLL shows no retry `MessageBox` (the editor asks), and it breaks on D3D12 debug-layer messages only when a debugger is attached (`unattended = !IsDebuggerPresent()`; the layer still writes to `OutputDebugString` either way). `ShutdownEngine` is a no-op when not initialized, after a failed initialization (D3D12 already cleaned up; a second `graphics::shutdown()` would crash, #128), and on a second call. Unlike Primal, `InitializeEngine` takes the engine root (UTF-16; the editor passes its resolved `MainWindow.DXForgePath`, issue #117) and compiles the shader sources under `<root>\DXForgeEngine\Graphics\Direct3D12\Shaders`, so an editor placed outside the repository still initializes; `compile_shaders()` without a folder keeps the working-directory-relative `..\..\` for `EngineTest`. `shaders\d3d12\shaders.bin` stays relative to the working directory, so the editor switches it to its exe folder first. `shaders.bin.source` next to it records the source folder it was built from; a different folder (or no record) rebuilds it even when the sources are older (issue #152). With an include folder given (or a `-I` in the extra arguments, as the editor passes), the working-directory-relative default is not added to `-I`, so headers from another engine tree never win (issue #150). The DXC loader (`ShaderCompilation.cpp`) caches only a successful load, so the editor's retry picks up a `dxcompiler.dll` put in place after a failure. Primal's native `EditorHost` launcher (Day 078) is not ported: it only exported the D3D12 Agility SDK symbols, and Primal itself removed it in Day 079 in favour of `ID3D12SDKConfiguration1`, which DXForgeEX uses for every executable (see the D3D12 runtime bullet under Engine, issue #155). `GetGraphicsRuntimeDescription` returns which D3D12 runtime was loaded; the editor logs it after `InitializeEngine` (a warning when it is the OS runtime). **Viewport API (Primal Day 082, issue #201):** `CreateRenderSurface` now also creates the swap chain surface and a per-viewport camera (`viewport_surface`), and the first viewport creates temporary lights in light set 0; `SetGeometryIds`/`RenderFrame` draw it, and `UpdateComponent`/`GetComponentId` edit entities. The editor does not call `RenderFrame` until Day 083, so the viewport stays undrawn on screen; `EngineUnitTests --render` exercises the path with a hidden window on WARP (`check_editor_viewports`). `EntityAPI.cpp`/`EngineAPI.cpp` share one `mutex`, and `CreateGameEntity` now reads the editor's rotation as degrees (`game.bin` still stores radians, as in Primal). Unlike Primal: `ShutdownEngine` releases every viewport's surface and camera first, because the editor calls it before `HwndHost` calls `RemoveRenderSurface`; without an initialized engine a viewport is only a window; a zero-sized viewport creates its surface at the next `ResizeRenderSurface`; `RenderFrame` skips surfaces smaller than a light culling tile; the two Day 083 fixes `RenderFrame` needs are included (`!lights[0].is_valid()`, an empty frame in `prepare_render_frame`).
- **EngineTest** (`Application`) — standalone native test harness (`Main.cpp`, `TestRenderer.cpp`, `Lights.cpp`, `Scripts.cpp`, `RenderItem.cpp`) for driving/visually testing the engine without the editor or a game project. Interactive: requires a window and a GPU, and gates on keyboard input — not suitable for CLI/CI.
- **EngineUnitTests** (`Application`) — headless automated test runner and headless mode. See `docs/dev/BuildAndTest.md`.
- **ContentTools** (`DynamicLibrary`) — offline asset pipeline: FBX import (`FbxImporter.*`, Autodesk FBX SDK), texture import (`TextureImpoter.cpp`, DirectXTex), procedural primitive meshes (`PrimitiveMesh.*`), tangent generation (MikkTSpace), normal-map detection. Consumed by the editor, not linked into the runtime engine.
- **DXForgeEditor** (C#/.NET WPF, `ConfigurationType` mapped to the Editor configs) — project browser/creation, scene & game-entity editing (undo/redo commands), content browser, texture/geometry editors, Visual Studio automation for generating and building per-game-project C++ solutions (`ProjectTemplates/*`, `GameDev/VisualStudio.cs`).
- **DXForgeImport** (C#/.NET console app, `DebugEditor`/`ReleaseEditor` only) — headless asset importer. See `docs/dev/DXForgeImport.md`.
- **DXForgeCli** (`dxforge.exe`, C#/.NET console app, `DebugEditor`/`ReleaseEditor` only) — `--load-project`: loads a `.dxproj` with the editor's code, writes the editor's `game.bin` and runs it with `EngineUnitTests --game-bin`. See "Project loading" in `docs/dev/BuildAndTest.md`.

## Engine

- **Platform abstraction**: `Platform/Platform.h` + `PlatformWin32.cpp` wrap OS window handling behind a platform-independent interface; `Window.h` is the cross-platform window handle type.
- **Graphics abstraction**: `Graphics/GraphicsPlatformInterface.h` defines a `platform_interface` struct of function pointers (surface, light, camera, submesh/texture/material, render) that each graphics backend fills in. `Graphics/Renderer.cpp` selects a backend (`graphics_platform::direct3d12/vulkan/opengl`) and forwards calls to it. **Only Direct3D12 (`Graphics/Direct3D12/`) is actually implemented**; the Vulkan/OpenGL folders exist as stubs for future backends — do not assume they work.
- **D3D12 runtime (Agility SDK, issue #155, Primal Day 079)**: the engine pins the D3D12 Agility SDK with the NuGet package `Microsoft.Direct3D.D3D12` (`DXForgeEngine/packages.config`, 1.620.1) and creates its device through `ID3D12SDKConfiguration1::CreateDeviceFactory(D3D12_SDK_VERSION, <engine module folder>\D3D12\)` (`Graphics/Direct3D12/D3D12Runtime.cpp`). `D3D12_SDK_VERSION` comes from the package's `d3d12.h`, so the header and the runtime cannot disagree. The folder is next to the module that contains the engine code (the exe for games, `EngineTest` and `EngineUnitTests`; `DXForgeEngineDLL.dll` for the editor), passed as an absolute UTF-8 path (works for folders outside the ANSI code page; relative paths would be resolved from the exe, not the working folder). Because every executable goes through the same device factory, no executable exports `D3D12SDKVersion`/`D3D12SDKPath` (Primal Day 078 did, from `EditorHost`; Day 079 dropped it), and neither developer mode nor the registry is needed. The debug layer comes from the factory too (`D3D12\d3d12SDKLayers.dll` in Debug configs), and root signatures are serialized with `ID3D12DeviceConfiguration1` of that device. The maximum feature level is queried with `ID3D12Device16::CheckFeatureSupport1(..., D3D12_SDK_VERSION)` when the device has it, falling back to `CheckFeatureSupport` (OS runtime): the Agility SDK debug layer reports the latter as deprecated (WARNING #989, issue #159). `DXGI_CREATE_FACTORY_DEBUG` is set only when `DXGIGetDebugInterface1` succeeds (Graphics Tools), independently of the D3D12 debug layer. **When the Agility SDK cannot be used** (no `D3D12\D3D12Core.dll`, a version mismatch, or an OS `d3d12.dll` without `ID3D12SDKConfiguration1`), the engine logs a warning and continues with the OS runtime (`D3D12CreateDevice` etc.), as before #155. `D3D12GetInterface` is resolved with `GetProcAddress`, never imported: an OS `d3d12.dll` that predates the Agility SDK lacks it, and a static import would make the loader fail before `main` (the exe/DLL import tables may only use d3d12.dll functions from Windows 10 1607; `render_run_test.py` and `engine_init_test.ps1` check this). After the device is created it finds the `D3D12Core.dll` actually loaded (path and file version) and logs one line to `OutputDebugString` (and to stderr when unattended), e.g. `[D3D12] runtime: Agility SDK 620 (D3D12Core 1.620.1.0, <path>)`; `graphics::runtime()` returns the same as `runtime_info`. **Deployment**: `DXForgeEngine.vcxproj` copies `D3D12Core.dll` (plus `d3d12SDKLayers.dll` for Debug configs) into its `OutDir\D3D12\` (`x64\<Config>\D3D12\`) after every build; `EngineTest`, `EngineUnitTests`, `DXForgeEngineDLL` and the editor all build into that same folder, and the game project template copies `$(DXForge_LibraryPath)D3D12\*.dll` next to the game exe (Debug/Release, i.e. the `Application` configs).
- **D3D12 backend** (`Graphics/Direct3D12/`): `D3D12Core` (device/queues/sync), `D3D12Surface` (swap chain per window, or one offscreen texture without a window for the headless `--render` mode, #127), `D3D12Resource`/`D3D12Helpers` (descriptor heaps, deferred resource release, free-list-backed id allocation), `D3D12Upload` (copy-queue GPU uploader), `D3D12Content` (GPU-side submesh/texture/material storage), `D3D12GPass` (depth prepass + geometry/lighting pass, draw-indirect), `D3D12Light`/`D3D12LightCulling` (tiled light culling via compute shader — frustum grid build + culling, see `Shaders/GridFrustums.hlsl`/`CullLights.hlsl`), `D3D12PostProcess` (fullscreen post pass). Engine HLSL shaders live under `Graphics/Direct3D12/Shaders/` and are precompiled offline into a `shaders.bin` blob referenced by `Renderer.cpp`'s `engine_shader_paths`. Since Primal Day 082 (#201): deferred releases wait one more round of frames (`force_release` at shutdown), fences are waited on without an event (`SetEventOnCompletion(value, nullptr)`), `renderer_option` (vsync, raytracing, msaa; `set_option`/`get_option`) controls presenting with vsync on by default, and vsync can be turned off only when DXGI supports tearing. Unlike Primal: the depth buffer keeps `PIXEL_SHADER_RESOURCE` in its read state (`PostProcess.hlsl` reads depth in a pixel shader), and `descriptor_heap::free` sets the deferred release flag before taking the heap's mutex (`process_deferred_releases` takes the two mutexes in the other order). As in Primal, a new deferred release resets its slot's wait, so a slot that gets a release every cycle is not reclaimed until the releases stop.
- **ECS**: `Components/Entity.*` is the game-entity container; `Transform`, `Script`, `Geometry` are components attached via generational IDs (`Common/Id.h`). `EngineAPI/*.h` are the public structs/handles (camera, light, game entity, transform/script/geometry component, input) exposed across the DLL boundary — these mirror internal types but are kept ABI-stable for the editor and game code. Transforms store a local frame (`right()`/`up()`/`front()`/`local_frame()`) derived from the rotation quaternion; there is no separate orientation setter (removed with Primal Day 086, issue #4) — change a direction by setting a rotation.
- **Content pipeline (runtime side)**: `Content/ContentToEngine.*` converts compiled asset blobs (meshes, textures, materials, shaders — see `asset_type`/`texture_flags` enums) into GPU resources via the active graphics backend; `Content/ContentLoader.*` handles loading the game DLL and engine shader blob (editor/dev builds only, guarded by `!defined(SHIPPING)`).
- **Content pipeline (offline side, `ContentTools`)**: separate from the runtime; produces the asset files `ContentToEngine` consumes. FBX scenes are traversed/packed into submesh+LOD hierarchies; textures go through DirectXTex import/compression; tangents are generated with MikkTSpace for normal mapping.
- **Game code**: each game project gets its own generated Visual Studio solution/project (from `DXForgeEditor/ProjectTemplates/*`), built via editor-driven VS automation (`GameDev/VisualStudio.cs`) and loaded as a DLL at runtime (`ContentLoader::load_game`).

## Editor (DXForgeEditor, C#/WPF)

- `GameProject/` — project creation/open (`NewProject.cs`, `OpenProject.cs`), the `Project`/`Scene` models, and the undo/redo command system backing entity/component edits.
- `Components/` — editor-side mirrors of engine components (transform, script, geometry) with multi-selection support, bound to WPF views. `Component.Load()`/`Unload()` (Primal Day 079, issue #32) run when `GameEntity.IsActive` changes: `Load()` before `EntityAPI.CreateGameEntity`, `Unload()` after `RemoveGameEntity`; `AddComponent` keeps an inactive entity inactive. `Components/Geometry.cs` holds a geometry asset GUID plus one `AppliedMaterial` per submesh (all LODs, in order): `Load()` uploads the geometry and the materials (saved ones first, `DefaultMaterial` for the rest) through `UploadedAsset`, and `EngineAPI.GeometryComponent` passes the content ID and the per-submesh material IDs to `DXForgeEngineDLL/EntityAPI.cpp`, which attaches `geometry::init_info` only when the content ID is valid. A missing asset or a failed upload is logged and the entity is created without geometry (no exception, no assert). When the editor opens a project, `Project.Load` registers the assets before deserializing (`ContentWatcher.Reset`, Primal Day 081), sets `Project.Current` (a static property, cleared by `Unload`), and logs and returns `null` on failure; a headless load does none of this and still throws. `Geometry.Load()` does nothing until `AssetRegistry.ContentFolder` is the project's `ContentPath` (a `.dxproj` whose saved `Path` is stale, because the folder moved), and `Project.LoadEntitiesWithAssets()` at the end of `Load` re-creates the active entities whose geometry is not loaded yet. `Project.Unload()` deactivates every entity (not only the scripted ones `UnloadGameCodeDLL` handles), so closing or switching projects releases the uploaded meshes and materials. Materials are saved in the `.dxproj` as `AppliedMaterialData` (material asset GUID, input GUIDs/names, surface values in scRGB) rather than by making `AppliedMaterial` a `[DataContract]` as Primal does, because `AppliedMaterial` builds its reference-counted upload state in its constructor (#145), which `DataContractSerializer` skips. Geometry is **not** written to `game.bin` (`Component.CanWriteToBinary` is false; `Project.WriteGameBinary` skips it with a warning): Primal Day 079 throws `NotImplementedException` there, which would crash the editor through the `async void` `RunGame`, and `content::load_game` has no geometry reader. So a scene's `game.bin` is byte-identical with or without Geometry components, and headless loading (`ProjectLoadEnvironment.Headless`) never calls `Load()`. Primal Day 080 adds the inspector view (`Editors/WorldEditor/GeometryComponentView.xaml`: name, icon, V/I/T/M for a single submesh, one tab per LOD otherwise, MULTI VALUE when the selected entities' geometry differs) and enables "Add Component → Geometry", which attaches `DefaultAssets.DefaultGeometry` (`DefaultCube.asset`, ContentTools' `create_cube` from Primal Day 075). The cube always has the fixed GUID `DefaultAssets.DefaultGeometryGuid` (`EnsureDefaultCube` recreates a file with another GUID): the asset lives next to each editor exe (per configuration and worktree) and projects store only the GUID, so a per-file random GUID as in Primal would make a project saved with one editor build lose its cube in another. Like the default material, default assets are not registered in the project's `AssetRegistry`; `Geometry.FindGeometry` returns the default asset for its GUID. Dragging a geometry asset from the Content Browser (`Utilities/Controls/ListViewEx.cs` keeps a multi-selection while a drag starts; the browser sends `DataFormats.FileDrop`) onto the view's drop border replaces the geometry of all selected entities, with undo/redo that also restores the per-submesh materials (`Geometry.GetMaterialsData`/`SetGeometry(guid, materials)`; Primal restores only the GUID). Unlike Primal, `SetGeometry` runs on the UI thread (no `Task.Run`, since the asset/engine calls have no locks yet, #171), `ComponentView` stays a `UserControl` and the views keep their names (#172), the applied-material placeholder is not ported (#173), and `AssetRegistry` has no cache file (#171).
- `DllWrappers/` — P/Invoke boundary calling into `DXForgeEngineDLL`.
- `Content/Material.cs` — material assets (Primal Day 077, issue #30): `Material` (shader groups from `Shader.cs`, default surface values, input names; saved as `.asset`) and `AppliedMaterial` (a material plus per-use surface values and input assets, packed by `PackForEngine()` in the layout `DXForgeEngineDLL/ResourceUpload.h` reads). `Content/Asset.cs`'s `UploadedAsset` reference-counts assets uploaded through `EngineAPI.CreateResource`. Unlike Primal, an `AppliedMaterial` registers its material's shaders per `Material` (first user uploads, last user removes), because `ShaderGroup.UploadToEngine()` does not add a reference for the same instance (#29). The engine is initialized at editor startup since issue #31; the first caller is the Geometry component (Primal Day 079, issue #32), which also records each `AppliedMaterial`'s material asset GUID (`MaterialGuid`, separate from the per-upload `Guid`). `Content/DefaultAssets.cs` saves `DefaultMaterial.asset` next to the editor exe from the default material shaders it compiles at startup, and rewrites it only when the compiled shaders change.
- `Content/ContentBrowser/`, `Editors/TextureEditor/`, `Editors/GeometryEditor/`, `Editors/WorldEditor/` — asset browsing and per-asset-type editors (texture detail/RGBA channel view, geometry/primitive preview, scene/world viewport with its own render surface).
- `GameDev/EnginePath.cs` — decides the engine path written into each game solution's `Directory.Build.props` (issue #117): the repo the running editor exe lives in (`x64\<config>\` two levels up, with `DXForgeEngine\EngineAPI`) wins, so a worktree's editor builds games against that worktree; otherwise the user env var `DXFORGE_ENGINE` (never rewritten, except by the existing `EnginePathDialog` when neither is valid). The choice is logged at startup and on every game build, as a Warning when it differs from `DXFORGE_ENGINE`. Headless check: `pwsh -NoProfile -File DXForgeEditor/Tests/engine_path_test.ps1` (CI runs it in the `Editor build` job).
- `Utilities/RenderSurface/` — hosts a Win32 D3D12 render surface inside WPF (HwndHost-style interop) for viewport rendering.
