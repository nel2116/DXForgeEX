# Build and test details

<!-- last-reviewed: 2026-11-07 -->

Reference for agents and contributors. The commands to run are in the root `AGENTS.md`; this file explains why they are the way they are. `README.md` is the Japanese overview for humans; details live here.

## Building

- Visual Studio 2022 (`PlatformToolset v143`, open `DXForge.sln`) or the CLI: root `build.ps1` wraps MSBuild (native) and `dotnet build` (editor) and can run the tests afterwards. It summarizes build output by default — errors verbatim, warnings folded into per-code counts.
- **Always build native projects through `DXForge.sln`**: directly invoking a `.vcxproj` makes `$(SolutionDir)` fall back to the project's own directory, breaking the `AdditionalIncludeDirectories` paths. `build.ps1` does this correctly via `/t:<ProjectName>`.
- **D3D12 Agility SDK** (issue #155): `DXForgeEngine/packages.config` pins `Microsoft.Direct3D.D3D12` 1.620.1. Since `DXForgeEngine` builds in every configuration, `Restore.ps1` restores it for `Debug`/`Release` too (only that project's `packages.config` there; the `*Editor` configs still restore all of them), so a fresh worktree restores and builds in one go. The package's own `Content` copy is turned off; `DXForgeEngine.vcxproj` copies the runtime into `x64\<Config>\D3D12\` itself (see `docs/dev/Architecture.md`). Bumping the version means editing `packages.config` and the `1.620.1` paths in `DXForgeEngine.vcxproj` (imports, the `EnsureNuGetPackageBuildImports` errors and `DXForgeAgilitySdkBin`); the SDK version passed at run time follows the header.
- **DXC (two copies, on purpose).**
  - `GetDXC.ps1` fetches the DirectX Shader Compiler package (`packages/DirectXShaderCompiler`); it downloads the *latest* DXC release whenever that folder is empty, so CI caches it to avoid GitHub API rate limits. Only `EngineTest` (runtime shader compilation) uses it, so `Restore.ps1` fetches it only when `EngineTest` is part of the build (`Debug`/`Release` with no `-Project`, or `-Project EngineTest`); `-Project EngineUnitTests` and the `*Editor` configs build offline without it (issue #61).
  - The editor-side shader compilation (`DXForgeEngineDLL`'s `CompileShader`, Primal Day 076, issue #29) uses a separate, version-pinned NuGet package `Microsoft.Direct3D.DXC` (`DXForgeEngineDLL/packages.config`, restored with the other `*Editor` NuGet packages); its targets copy `dxcompiler.dll`/`dxil.dll` next to `DXForgeEngineDLL.dll` (= the editor's output folder).
  - `ShaderCompilation.cpp` (shared with `EngineTest`) loads DXC at run time with `LoadLibraryExW` from its own module's folder instead of linking `dxcompiler.lib`, so a missing DXC only fails the compilation (logged) instead of making `DXForgeEngineDLL.dll` unloadable.
- **FBX SDK**: `ContentTools` needs it, so it is out of CI scope (and the `Debug`/`Release` configs don't build it anyway). The location is the `FbxSdkDir` property in `ContentTools/FbxSdk.props` (defaults to the standard 2020.3.7 install path; override via env var or `/p:FbxSdkDir=`; a missing SDK fails early with a clear error). `/p:` global properties are immutable inside the project, so normalize into a *different* property name rather than reassigning `FbxSdkDir`.
- **ATL is not needed** (issue #146). `get_script_names()` (`Script.cpp`, `USE_WITH_EDITOR`) used to build its `SAFEARRAY` with ATL's `CComSafeArray`/`A2BSTR_EX`, so the `*Editor` configs of `DXForgeEngine`/`DXForgeEngineDLL` failed with `C1083: Cannot open include file: 'atlsafe.h'` on machines without the VS "C++ ATL" component, including the GitHub runner. It now uses only OLE Automation (`script::detail::make_script_names_safe_array()`: `SafeArrayCreateVector(VT_BSTR)`, `SafeArrayPutElement`, names decoded with `CP_ACP` like `A2BSTR_EX`, because the editor marshals the name back to `GetScriptCreater` as ANSI and the DLL looks the script up by the hash of those bytes, so UTF-8 decoding would break the round trip; `oleaut32.lib` via `#pragma comment`), tested in `EngineUnitTests/Tests_Script.cpp`. Do not reintroduce ATL headers: CI would stop building the DLL. To check locally, build with the ATL include path hidden: `MSBuild DXForge.sln -t:DXForgeEngine:Rebuild;DXForgeEngineDLL:Rebuild -p:Configuration=DebugEditor -p:Platform=x64 -p:VC_ATLMFC_IncludePath=<missing folder>`.

## `build.ps1`

Run from PowerShell 7+ (`pwsh`).

```powershell
./build.ps1                                                      # native + editor, DebugEditor
./build.ps1 -Configuration Debug
./build.ps1 -Target native -Project EngineUnitTests              # fastest loop
./build.ps1 -Target editor
./build.ps1 -Target native -Project EngineUnitTests -RunTests    # tests set the exit code
./build.ps1 -Target native -Project EngineUnitTests -RunTests -Json   # plus a one-line JSON summary
```

| Parameter | Values | Default |
|---|---|---|
| `-Configuration` | `Debug` / `DebugEditor` / `Release` / `ReleaseEditor` | `DebugEditor` |
| `-Target` | `native` / `editor` / `all` | `all` |
| `-Project` | A project in `DXForge.sln` (`-Target native` only). `EngineTest`/`EngineUnitTests` alone are built in the matching `Debug`/`Release` config even under an `*Editor` config, which lacks them (#129) | whole solution |
| `-RunTests` | Switch. After the build, runs `EngineUnitTests.exe` and the headless tests (`EngineUnitTests/Tests/headless_run_test.py`, `render_run_test.py`; needs python). For an `*Editor` whole-solution build, `-Target editor` or another `-Project`, it first builds `EngineUnitTests` in the matching `Debug`/`Release` config (so a stale exe is never run; restoring the Agility SDK package first unless `-NoRestore`). Skipped when the build fails | - |
| `-NoRestore` | Switch. Skips `Restore.ps1` before the native build | - |
| `-WarningsAsErrors` | Switch. Warnings fail native and editor builds (CI) | - |
| `-Json` | Switch. One-line JSON summary on stdout | - |
| `-DetailedLog` | Switch. Full build tool output | - |

### Restoring `packages/` (`Restore.ps1`)

`packages/` is git-ignored, so a new clone or worktree starts empty. `build.ps1` calls `Restore.ps1` before the native build, and it fetches only what is missing; nothing has to be copied by hand.

- **NuGet** (`directxtex_desktop_win10` in `ContentTools/packages.config`, `Microsoft.Direct3D.DXC` in `DXForgeEngineDLL/packages.config`, the `PackageReference`s of `DXForgeEditor`/`DXForgeImport`): when a `packages/<id>.<version>` folder, or the `obj/project.assets.json` of any SDK-style `.csproj` in `DXForge.sln`, is missing, it runs `MSBuild DXForge.sln -t:restore -p:RestorePackagesConfig=true` once (no `nuget.exe`). The `.csproj` files are listed from the solution, so new C# projects are covered, and deleting only `obj` no longer gives `NETSDK1004` in an `*Editor` native build, which also builds the C# projects (#116). These are `*Editor`-only; `Debug`/`Release` restore only the Agility SDK (above). Test: `pwsh -NoProfile -File Tests/Restore.Tests.ps1` (also in CI's `Editor build`).
- **DXC** (`packages/DirectXShaderCompiler`): see the DXC bullet above. `GetDXC.ps1` uses the GitHub API with `GITHUB_TOKEN`/`GH_TOKEN` when set (CI passes `GITHUB_TOKEN`) for a higher rate limit, retries with a delay, and says so when it fails because of the rate limit.
- When everything is present it only checks files, without network access (measured: tens of ms). It runs alone too (`./Restore.ps1 -Configuration DebugEditor`). To update DXC to the latest release, delete `packages/DirectXShaderCompiler` first.

## Warnings as errors

- Native: zero warnings in both configs. Local builds stay lenient; CI passes `-WarningsAsErrors`. **`/p:TreatWarningAsError=true` does not work for C++ projects** (a global property never reaches `ClCompile` item metadata, so the compiler still gets `/WX-`); the gate is an `ItemDefinitionGroup` in the root `Directory.Build.props`, switched on by `/p:DXForgeWarningsAsErrors=true`. Verified: with the switch the compile line carries `/WX` and an injected `C4189` fails the build.
- Editor: also zero warnings (issue #9: 272 unique nullable warnings fixed with `<Nullable>enable</Nullable>` kept). The same switch passes `-p:TreatWarningsAsErrors=true --no-incremental` to `dotnet build` (full rebuild, because an up-to-date incremental build re-emits no warnings). Verified: an injected `CS8602` fails the build.
- History of "do not silence a real defect": the two `C4100` warnings that existed before the gate marked a genuine bug — `transform::set_orientation` was an empty body reachable from the public API, so the value was silently dropped (fixed in issue #4 by porting Primal Day 086, commit `db1c19d`).

## Encodings (`.editorconfig`, enforced by `Tests/check_conventions.py`)

- `.c/.cpp/.h/.hpp` are UTF-8 BOM + tabs, `.cs`/`.xaml`/`.ps1` are UTF-8 BOM. Without a BOM, MSVC misdetects a file as the local codepage (Shift-JIS) and corrupts the token stream, producing unrelated-looking cascading compile errors at/after the first Japanese comment.
- `.hlsl`/`.hlsli` are UTF-8 BOM + 4 spaces (the 8 engine shaders with Japanese comments were converted from Shift-JIS in issue #7), **except** the fxc-compiled ones under `ContentTools/` and `DXForgeEditor/`, which must stay BOM-less. Both halves were verified: the engine shaders need the BOM because `Shaders/SharedTypes.h` `#include`s `CommonTypes.hlsli` into the C++ build (BOM-less UTF-8 there gives `C4819` → `/WX` failure), and DXC accepts either; fxc (`ContentTools/CompileShaders.cmd`, the WPF pixel shader, Visual Studio's HLSL build for SM 5.x) rejects a BOM with `error X3000: Illegal character in shader file`, directly or through `#include`. ASCII-only engine shaders without a BOM are harmless and are not flagged.
- **Japanese in a narrow string literal** fails CI: runners use code page 1252, MSVC converts narrow literals to the execution charset, and each Japanese character gives `C4566` → `/WX` failure (real locale-dependent data, not CI noise). Comments are fine. Use the wide API (`OutputDebugStringW(L"...")`, as `D3D12Core.cpp` does). The symptom is Debug-only when the code sits inside `#if _DEBUG`.
- The same applies to **any literal, even `L"..."`, inside the arguments of a macro that stringizes them** (`CHECK`/`REQUIRE` in `EngineUnitTests/MicroTest.h`, `DXCall`, `DXC_CALL`): `#expression` turns the whole argument into a narrow literal (issue #149). Move the literal into a constant outside the macro. The check (`stringize`) knows the repository's stringizing macros from `STRINGIZING_MACROS` plus `#define`s in the checked file; `check_conventions_test.py` fails when a new one is defined elsewhere and not added to the list.

## MSBuild `Exec` and `NoDefaultCurrentDirectoryInExePath`

Agent shells (Claude Code, Codex) set `NoDefaultCurrentDirectoryInExePath`, so cmd.exe does not look for a command in the working directory. An `<Exec Command="Script">` that relies on `WorkingDirectory` to find `Script.cmd` fails with `9009` there — and only when the target actually runs, so an up-to-date checkout hides it. Call scripts by full path (`&quot;$(ProjectDir)Script.cmd&quot;`), as `ContentTools.vcxproj`'s `CompileShaders` does since issue #154.

## Tests

- **EngineUnitTests** (Debug/Release only, no Editor configs): links `DXForgeEngine` but needs no window or GPU device; one `Tests_<module>.cpp` per module. Uses a dependency-free micro test framework (`MicroTest.h`: `DXFORGE_TEST_CASE`/`CHECK`/`REQUIRE`). Run `x64/<Debug|Release>/EngineUnitTests.exe [--json] [--interactive]`: exit 0 all passed, 1 a check failed (expression, file and line are printed). An `assert` or `abort()` in the code under test shows no dialog: the assert text and `[ABORT] <test case>` go to stderr and it exits 3 at once, with nothing on stdout (results are printed after all cases, so no JSON either); treat any code other than 0/1 as aborted. `--interactive` keeps the CRT dialog for attaching a debugger (#89). Release defines `NDEBUG`, which compiles out the `assert`s that `free_list`/`Id` rely on, so CI runs both configs.
  - Adding a test: create `EngineUnitTests/Tests_<target>.cpp` (UTF-8 BOM and the file header, like every C++ file), add it to `ClCompile` in `EngineUnitTests.vcxproj` and `.vcxproj.filters`, and write `DXFORGE_TEST_CASE(name) { CHECK(...); REQUIRE(...); }` with `#include "MicroTest.h"` and `#include "CommonHeaders.h"`. A failed `CHECK` continues the case; a failed `REQUIRE` ends it.
- **Headless mode** (issue #11, first step): `EngineUnitTests --game-bin <path> --frames <N> [--dt s] [--json]` loads a `game.bin` through the same `content::load_game(path)` the game exe uses, calls `script::update(dt)` N times, and reports the last frame's entity transforms as JSON on stdout (logs on stderr; argument errors are JSON too): `{"mode":"headless","game_bin":"...","frames_requested":10,"frames_run":10,"dt":0.016,"success":true,"exit_code":0,"error":null,"entity_count":1,"entities":[{"id":0,"position":[10,0,0],"rotation":[0,0,0,1],"scale":[1,1,1]}]}`, with `"error":{"code":"script_not_found","message":"..."}` on failure; `entities` are the live entities after the last frame. `--dt` defaults to 0.016. No window, no GPU, no Renderer; the loop/argument parsing lives in `DXForgeEngine/Core/Headless.{h,cpp}` (non-`SHIPPING` only), and scripts must be statically registered in the runner exactly like in a game exe (currently only `EngineUnitTests/HeadlessTestScripts.cpp`). Exit codes: 0 ok (a 0-entity `game.bin` is a valid empty scene, deliberately unlike Primal — #107), 2 usage, 3 abort, 10 not found, 11 unreadable/empty, 12 invalid format, 13 unknown component, 14 unregistered script, 15 entity creation failed (`--help` lists them). `python EngineUnitTests/Tests/headless_run_test.py [--config Release]` checks it as a separate process; `build.ps1 -RunTests` (so CI) runs it too. Not yet there: script-driven operations, rendering a `game.bin`, hooking up the #10 ContentTools CLI (`.dxproj` loading is `dxforge --load-project`, below). This is the start of the "AI/CLI-friendly engine" direction (see `README.md`) — extend this runner rather than reviving `EngineTest` for anything that must run unattended.
- **Project loading** (issue #11): `x64/<DebugEditor|ReleaseEditor>/dxforge.exe --load-project <.dxproj> --frames <N> [--dt s] [--scene name] [--runner exe] [--keep-game-bin path] [--json]`, or `--export-game-bin <path>` to only write the `game.bin`. C# console app `DXForgeCli` (assembly `dxforge`, `*Editor` configs only, built by `build.ps1 -Target editor` after `DXForgeImport` with `BuildProjectReferences=false`). It does **not** reimplement `.dxproj` or `game.bin`: it calls the editor's `Project.Load` and `Project.WriteGameBinary` (extracted from `SaveToBinary`; `InternalsVisibleTo("dxforge")`), writes the `game.bin` to `%TEMP%\dxforge\<guid>\` and runs `EngineUnitTests --game-bin ... --json` as a child process (default `x64/<Debug|Release>/EngineUnitTests.exe` next to its own folder, by `DEBUG`), then re-emits the runner's JSON with `mode`/`project`/`scene`/`game_bin`/`runner` and each entity's editor `name` added. Stdout is only the JSON; the runner's stderr is forwarded to stderr.
  - Loading side effects are switched off by `GameProject/ProjectLoadEnvironment.Headless` (default `false`; only `dxforge` sets it): `Project.OnDeserialized` skips `BuildGameCodeDLL` (Visual Studio COM + `DXForgeEngineDLL`), `Scene.OnDeserialized` skips `entity.IsActive = ...` (`EngineAPI.CreateGameEntity`). The WPF `Application` is created but never `Run()` (same as `DXForgeImport`, for `Logger`).
  - Pitfalls handled in `dxforge`: `Project.OnDeserialized` is `async void`, so an exception in it (e.g. a `.dxproj` without `<Scenes>` → `ArgumentNullException`) never leaves `ReadObject`; it is posted to the `SynchronizationContext` (with none, it would crash the process on the thread pool), so the load runs under a capturing context → exit 31. `Debug.Assert` in the editor's `OnDeserialized` (no active scene, missing collections) would `FailFast` in `DebugEditor`; `Trace.Listeners` is replaced during the load so they go to stderr as warnings and `dxforge` checks the state itself. DataContract never runs field initializers, so missing `<GameEntities>`/`<Components>` leave the collections `null` (→ 31).
  - `Geometry` components are not written to `game.bin` (issue #32; see `Components/` in `docs/dev/Architecture.md`): export and run both succeed with a warning per skipped component on stderr, and the JSON is unchanged.
  - Scenes with a `Script` component are rejected with 33 (the runner only has its statically registered test scripts; loading the game code DLL is a later step). `--export-game-bin` still writes them.
  - Exit codes: the runner's are passed through (0, 2, 3, 10–15; with no JSON on stdout, 3 is `runner_aborted`, anything else 35); its own are 2 (`invalid_arguments`, vs. the runner's `usage_error`), 30 project not found, 31 invalid project, 32 scene not found, 33 scripts unsupported, 34 runner not found, 35 runner failed to start / unreadable JSON / JSON `exit_code` ≠ process exit code, 36 `game.bin` write failed, 39 unexpected.
- **Scene operations** (issue #183): `dxforge --load-project <.dxproj> --ops <file> | --op '<json>' [--dry-run] [--json]` changes or reads a scene without the editor UI. The implementation is `DXForgeEditor/Automation/` (`SceneOpDocument` validates, `SceneOpRunner` runs, `ProjectEditorLock`); `Program.cs` only calls it, so a future editor route (#184) runs the same code. Format is `DXForgeCli/Schema/ops.schema.json` (copied next to the exe; `--help` prints the path). Validation is hand-written (no schema library); `DXForgeCli/Tests/ops_cli_test.ps1` checks that the schema and `SceneOpDocument.AllowedKeys`/`RequiredKeys` agree, so **change both together**.
  - Example: `{"ops":[{"op":"create-entity","as":"box","name":"Box"},{"op":"set-transform","target":"$box","position":[0,1,0],"rotation_deg":[0,90,0]},{"op":"add-component","target":"$box","type":"geometry","asset":"default:cube"}]}`.
  - Read ops: `list-scenes`, `list-entities` (`scene` optional), `get-entity` (`target`). Change ops: `create-entity` (`name`, `scene`, `as` optional; the result has the GUID), `remove-entity`, `rename` (`name`), `set-enabled` (`enabled`), `set-transform` (`position`, `rotation_deg` or `rotation_rad`, `scale`), `add-component` (`type` `transform`/`script` (`name`)/`geometry` (`asset`)), `remove-component` (`type`), `set-geometry` (`asset`), plus the scene and `import-asset` ops below.
  - Targets: `guid:<GUID>`, `name:<name>` (41 if not unique), `index:<scene>/<n>`, `$<alias>` (an `as` of an earlier `create-entity` in the same document). Assets: `guid:<GUID>`, `path:<path relative to Content>`, `default:cube`. Results go in `results` per op; a failure's place is in `error.op_index`/`error.key`.
  - Saving: one save at the end, only if an op changed a value and all succeeded (`<file>.<GUID>.dxforge-tmp` in the same folder, then `File.Move` over the file). Parallel runs on one project do not corrupt it, but the last save wins and earlier changes are lost; there is no lock against this. Loads no longer collide with each other (`Serializer.FromFile` opens with `FileAccess.Read` + `FileShare.Read`, so parallel `list-entities` all exit 0 and a read-only `.dxproj` can be read, #193), but a save's replace can still collide with another run's load and fail with 43 (`FileShare` is deliberately not widened); a failed run's changes are not saved. Target is the file passed in, not `Project.FullPath` (the saved `<Path>` can be stale). JSON always has `changed`/`saved`; on failure both are false and the file is byte-identical. `--dry-run` runs everything in memory, never saves, and says so on stderr.
  - Check order: 2 → 30 → 40 → 31 → 44 → 41/42 → 43. Codes: 40 format/schema (whole document is checked before anything runs; `error` has `op_index` and `key`), 41 entity/scene/asset/source not found or selector matches several, 42 operation failed (component exists/missing, removing Transform, asset not a mesh, last or active scene, import failed), 43 save failed or imported files could not be moved into `Content`, 44 editor has the project open.
  - Scenes: `create-scene {name}` adds an inactive scene (42 `scene_exists`). `remove-scene {scene}` removes it with its entities (41 not found/duplicate name, 42 `last_scene`, 42 `scene_active`); a `$alias` into a removed scene is 41. `set-active-scene {scene}` is `changed:false` when already active.
  - `import-asset {source, folder?, settings?}`: `source` is absolute only, `folder` is relative to `Content` (no `..`), `settings` become the importer's `--set Name=Value`. It runs `DXForgeImport.exe` as a separate process (no duplicated import code, a native crash in `ContentTools` is just a failed op), 10 minute timeout then kill. The default is next to `dxforge.exe` (`x64/<config>/`, both are built by `-Target editor`), `--importer <exe>` overrides it (ops mode only). Results have `assets` (`path`, `guid`, `type`) and `warnings`; later ops in the same document can use `path:`/`guid:` for them.
  - Staging (`SceneOpAssetStaging`): the importer writes to `<project>\.dxforge-import-<GUID>\<op index>\<folder>` on the same volume, with `--sources-output` pointing at the final `Content` folder so no `.asset` keeps the staging path. After all ops succeed the files move into `Content`, then the `.dxproj` is saved, so it never points at a missing asset; a failed move or save removes what was moved and the folders made for it (43). `--dry-run` and failures only delete the staging folder. An import-only document is `changed:true` and saves once. Existing files are never overwritten (42 `asset_exists`, also for two imports in one document): `Geometry.Save` inherits the GUID from the file it overwrites, so a reimport through staging would change GUIDs. What cleanup could not delete is listed in `leftover_paths` (always in the JSON). A killed process can leave `.dxforge-import-*` in the project folder, never in `Content`. Each staging folder has a `staging.lock` the owner holds with `FileShare.None | Inheritable`: the OS closes the handle when the process dies, and the importer inherits it, so killing only `dxforge` keeps the folder "in use" until the importer ends (`ProjectEditorLock` cannot tell this: only editors hold it, `dxforge` only probes it). The first thing a non-`--dry-run` document with a change op does after the 44 check is `SceneOpAssetStaging.SweepAbandoned`, once per run: a `.dxforge-import-<32 hex>` whose lock opens with `FileShare.None` is deleted; a sharing violation is left alone silently; a folder with no lock (from before this change, or the instant of creation) or one it cannot check is kept with a warning on stderr (delete it by hand if no `dxforge` uses it). What it could not delete is in `leftover_paths` and the next run retries; the operation still succeeds and stdout's JSON keeps its shape.
  - Importer exit codes: 3 → 41 `source_not_found`; 4 → 42 `import_unsupported_format`; 5 → 42 `import_invalid_settings`; 7 or a missing exe → 42 `importer_unavailable`; anything else (1, 10, timeout, crash) → 42 `import_failed`.
  - Test: `pwsh -STA -NoProfile -File DXForgeCli/Tests/ops_cli_test.ps1 [-Configuration ReleaseEditor] [-RequireRunner] [-RequireRealImporter] [-FbxFile x.fbx] [-LodFbxFile x.fbx] [-MultiLodFbxFile x.fbx]`. CI has no FBX SDK, so `fake_importer.cmd`/`.ps1` stands in: its `--input` is a JSON of instructions (`assets`, `mkdir`, `sleep`, `args_log`, `errors`, `warnings`, `no_json`, `exit`). Without `ContentTools.dll` the real-importer section is a SKIP; run it locally with `-RequireRealImporter` (build `./build.ps1 -Target native -Configuration DebugEditor -Project ContentTools` first) when changing the import path. It imports `box.fbx`, an FBX with an embedded texture and an FBX with several LOD groups (made by `DXForgeImport/Tests/make_multilod_fbx.py` unless `-MultiLodFbxFile` is given) without `--importer`, then checks the raw `.asset` bytes for the staging path and that every asset of the LOD groups reached `Content`.
  - Editor lock: while `MainWindow.DataContext` is a project, the editor holds `<Project.Path>.DXForge\editor.lock` (`FileShare.ReadWrite`, so several editors can hold the same project; closing one keeps the lock for the others, and the last to close deletes the file by reopening it with `FileShare.None` + `DeleteOnClose`). After a crash the OS closes the handle, and a leftover file nobody holds is not treated as locked. Nothing scans `.DXForge`, and `ContentWatcher` only watches `Content\`. `dxforge` probes with `FileShare.None`: it looks in both the folder of the given file and the saved `<Path>`; a sharing violation, or being unable to tell, means 44 for any document with a change op, including `--dry-run`. Read-only ops always pass. A project whose saved `<Path>` folder no longer exists gets no lock (logged). The moment between the check and the save (~0.3 s) is not covered.
  - No engine: `Scene.AddEntityWithoutEngine`/`RemoveEntityWithoutEngine` and `GameEntity.RemoveComponentWithoutEngine` exist because the UI paths toggle `IsActive`, which calls `EngineAPI`. No undo entries. Assets are looked up by reading `.asset` headers under the given file's `Content\` (not `AssetRegistry`, not `Project.ContentPath`). `default:cube` writes only `DefaultGeometryGuid`, so no file is needed. Scripts cannot be verified without the game code DLL: they are allowed, with a warning in the result; such a scene still gets 33 from `--frames`.
  - `GameEntity.EntityGuid` (`<a:Guid>` in `.dxproj`, not in `game.bin`, unlike Primal) is what `guid:` selects. A `.dxproj` without it gets new GUIDs on every load until something saves; use `name:`/`index:` until then. `index:` and `scene` fail with 41 (`ambiguous_target`) when two scenes share the name, which the editor does not forbid. Test projects under `DXForgeCli/Tests/Projects/` have fixed GUIDs.
  - Test: `pwsh -STA -NoProfile -File DXForgeCli/Tests/load_project_cli_test.ps1 [-Configuration ReleaseEditor] [-Runner exe] [-RequireRunner]`, with the fixtures `DXForgeCli/Tests/Projects/{TransformOnly,WithScript,WithGeometry}` (written by the editor's own `Serializer.ToFile`; the broken variants are generated in `%TEMP%`). It checks that `--export-game-bin` bytes == the editor's `SaveToBinary` (called by reflection with `Project.Path` pointed at `%TEMP%`) == bytes built from the format, and the run results (ids, names, positions, rotation quaternions from `System.Numerics.Quaternion.CreateFromYawPitchRoll(y, x, z)`, scales). For `WithGeometry` (the `TransformOnly` entities plus two Geometry components) it also checks the skipped-component warnings, that the `game.bin` equals the Geometry-less bytes, and that the saved geometry/material data survives a load → `Serializer.ToFile` → load round trip. It also checks the Day 080 pieces that need no GUI (#32): `Geometry.SetGeometry(guid)` starts from the default materials and `SetGeometry(guid, GetMaterialsData())` (the drop's undo) restores the per-submesh materials, `MSGeometry` does not show MULTI VALUE when no selected geometry is loaded, `Geometry.FindGeometry` resolves `DefaultAssets.DefaultGeometry` by GUID, and `ComponentFactory` creates a Geometry with the given asset. Without the runner the run cases are skipped unless `-RequireRunner` (CI's `Editor build` job builds `EngineUnitTests` in `Debug` and passes it).
- **Headless render** (issue #127, stages 1–4): `EngineUnitTests --render --frames <N> --width <w> --height <h> --screenshot <png> [--adapter warp|hardware] [--json]` draws a fixed scene built in code (`EngineUnitTests/HeadlessRender.cpp`: a sphere and a floor generated as `static_normal` meshes in the `ContentToEngine` blob format, one directional + one point light, a fixed camera, no IBL) into an offscreen surface, reads it back and writes an 8-bit sRGB PNG with WIC. No window, no swap chain; the default adapter is WARP (`IDXGIFactory4::EnumWarpAdapter`), `hardware` is the existing `determine_main_adapter()` choice. Width/height must be 16..16384 (`graphics::min_offscreen_surface_size` = the light culling tile size; smaller sizes hit the `delight::cull_lights()` assert, so `create_offscreen_surface()` returns an invalid surface for them and for a failed texture allocation). Exit codes 20 graphics init, 21 shaders unavailable, 22 render/read back (incl. Debug debug-layer ERROR/CORRUPTION), 23 PNG write; 2 (also: combined with `--game-bin`) and 3 as above. `--json` prints one line with `mode` (`render`), `screenshot`, `frames_requested`/`frames_run`, `width`/`height`, `adapter`/`adapter_name`, `success`, `exit_code`, `error`, `d3d12_runtime` and `pixel_hash` (FNV-1a 64-bit of the written RGB8 pixels, row by row from the top left). The PNG is the `R16G16B16A16_FLOAT` target clamped to [0, 1] and converted to sRGB, without tone mapping (same look as the window).
  - Engine side: `graphics::create_offscreen_surface(w, h)` + `surface::read_back()` (`Renderer.h`), `graphics_init_info { adapter, unattended }` passed to `graphics::initialize()`. An offscreen `d3d12_surface` owns one `R16G16B16A16_FLOAT` texture created in `COMMON`; since `D3D12_RESOURCE_STATE_PRESENT == COMMON`, `render_surface()` is unchanged and `present()` is a no-op for it. `unattended` (Debug only) skips `SetBreakOnSeverity` — a `__debugbreak` without a debugger is just a crash — and `graphics::flush_debug_messages()` prints WARNING+ to stderr instead; the log says whether the debug layer and the DXGI debug layer were enabled. With the Agility SDK the D3D12 debug layer is `D3D12\d3d12SDKLayers.dll`, so it is available even without Graphics Tools; `DXGI_CREATE_FACTORY_DEBUG` is only set when `DXGIGetDebugInterface1` succeeds (without Graphics Tools the factory creation itself used to fail). The log and the `--json` output (`d3d12_runtime`: `source` `agility`/`os`, `sdk_version`, `core_version`, `core_path`, `fallback_reason`) show which D3D12 runtime was loaded (#155).
  - Shaders are compiled at run time with DXC exactly like `EngineTest` (`ShaderCompilation.cpp` is compiled into `EngineUnitTests` against the Windows SDK's `dxcapi.h`, DXC is loaded with `LoadLibraryExW`), so the offline `-Project EngineUnitTests` build (#61) still needs no DXC. At run time `dxcompiler.dll`/`dxil.dll` must sit next to the exe: a post-build step copies them from `packages/DirectXShaderCompiler` when that folder exists and does nothing otherwise. Shader sources are found at `..\..\` from the exe, so the mode changes the working directory to the exe folder after making `--screenshot` absolute.

Not yet there: drawing a `game.bin`, IBL, scene/camera arguments.
  - **Baseline comparison** (#127 stages 5–6): the same script compares the first WARP render with `EngineUnitTests/Tests/baselines/render_warp_320x240_<Debug|Release>.png` (one per configuration, since Debug and Release pixels differ). The configuration comes from `--config`, or from the exe's folder name (`x64/<config>/`, which is how `build.ps1 -RunTests` passes it); if neither tells, the comparison is skipped (a failure under `DXFORGE_REQUIRE_RENDER_TEST=1`). A pixel fails when any RGB8 channel differs by more than 1 level (`BASELINE_TOLERANCE`); one failing pixel fails the test. WARP is bit-identical locally and on the runner, so 1 level only absorbs a possible WARP drift; the number of pixels within 1 level is printed. On failure it prints the count, the max diff and the bounding box, and writes `expected.png`, `actual.png` and `diff.png` (expected | actual | diff side by side; red = over the tolerance, yellow = within, the rest is the darkened expected image) to `%TEMP%\dxforge_render_diff\<config>\` or `DXFORGE_RENDER_DIFF_DIR` (CI uploads it as the `render-diff-<configuration>` artifact). Each comparison first deletes only those three files (the folder itself only when it is then empty, since `DXFORGE_RENDER_DIFF_DIR` may point at an existing folder), so nothing is left on success. `--adapter hardware` is not compared (GPUs/drivers differ: an RTX 2070 SUPER differs from WARP in 18 pixels by 1 level); the difference is only printed. WARP is the OS's `d3d10warp.dll`, not pinned with the `Microsoft.Direct3D.WARP` NuGet package; pin it if a runner image update ever breaks the comparison.

## CI (`.github/workflows/ci.yml`)

On push to `main`/`develop` and on every PR: native build + `EngineUnitTests` + headless test + headless render test (WARP on the GPU-less runner, `DXFORGE_REQUIRE_RENDER_TEST=1`) in `Debug` and `Release` with `-WarningsAsErrors` (the render test includes the baseline comparison; on failure the diff images are uploaded as `render-diff-<configuration>`), then a WARP screenshot uploaded as the `render-warp-<configuration>` artifact; the `Editor build` job runs the file-convention check, `dotnet build` of the editor, `DXForgeImport` and `dxforge` with `-WarningsAsErrors`, builds `EngineUnitTests` (`Debug`) as the runner for `load_project_cli_test.ps1 -RequireRunner`, builds `DXForgeEngineDLL` (`DebugEditor`, `-WarningsAsErrors`; possible without ATL since issue #146), and runs the headless script tests listed above, including `material_asset_test.ps1 -RequireEngineDll` and `editor_shader_compilation_test.ps1` against that DLL.

## Token cost of build output (measured)

The native MSBuild log is ~7,400 characters at default verbosity. `dotnet build` of the editor was **~132,000 characters** while it had 588 nullable warnings (272 unique, printed twice because of the WPF temp project); after issue #9 the raw minimal-verbosity log is ~470 characters. `build.ps1` still summarizes by default so a regression cannot flood a session again.
