# DXForgeImport (headless asset importer, issue #10)

C#/.NET console app, built only in `DebugEditor`/`ReleaseEditor` (like the editor).

```
DXForgeImport --input <file> --output <folder> [--type auto|geometry|texture] [--settings import.json] [--set Name=Value] [--sources-output <folder>] [--json]
```

It writes the same `.asset` files as the editor's drag-and-drop import (FBX → geometry, images → texture; IBL prefiltering and primitive meshes are not exposed yet).

## Design

- It does **not** reimplement the `.asset` format: it `ProjectReference`s `DXForgeEditor` (`InternalsVisibleTo("DXForgeImport")`) and calls the editor's own `Content` code (`ContentHelper.CreateAsset`/`GetAssetName`/`GetAssetFullPath`, `Asset.Import`/`Save`), so the format stays implemented in one place.
- The editor's dependencies on an open project are swapped through `Content/ContentImportEnvironment.cs` (`TempFolder` for the FBX temp copy, `ImportEmbeddedFiles` for `.fbm` embedded textures; both `null` in the editor = unchanged behavior) and `Logger.MessageLogged` (synchronous log event → stderr/JSON).
- WPF is still needed (logger dispatcher, geometry icon rendering via `GeometryView`): the CLI creates a plain `Application` on its STA main thread, merges only `DXForgeEditor;component/Dictionaries/EditorColors.xaml` (the editor's `App` is not used: its `App.xaml` dictionaries use `pack://application:,,,/...`, which resolves against the *entry* assembly, and it has `StartupUri`), never calls `Run()`, and never shuts the dispatcher down (`Logger.Log` is `async void` and awaits `BeginInvoke`; a stopped dispatcher would throw out of it).
- No window, project or GPU window is needed (texture compression creates a windowless D3D11 device and falls back to the CPU).
- Embedded FBX textures are copied from the temp `.fbm` into `<output>/<fbx asset name>.fbm/` before importing, so the texture `.asset`'s `Sources` (used by the editor's reimport) does not point into the deleted temp folder. The copy rule lives in one place, `ContentHelper.CopyEmbeddedMedia` (image extensions only; failures come back as `EmbeddedMediaCopy.Error`, not exceptions), and `Geometry.ImportFbx` runs it for both the editor and the CLI, so `ImportEmbeddedFiles` receives the copies (#111: the editor used to import straight from `Project.TempFolder`, which `Project.Unload` deletes).
- `--sources-output <folder>` is for callers that use `--output` as a staging folder and move the files afterwards (`dxforge` `import-asset`, #183): before `Save()`, texture `Sources` under `--output` are rewritten to the same relative path under this folder (`Import()` has already read the real file). Sources outside `--output` stay as they are.
- A geometry save is checked against `Geometry.LODGroupCount` and against errors logged during `Save()`, because `Geometry.Save()` catches its own exception and returns only the files written so far (partial save → exit 1, written files stay in `files`).
- A failed FBX import (`ContentToolsAPI.ImportFbx` → `GeometryFromSceneData`) is reported as `false` from `Geometry.Import()`, not as an exception, since the editor reaches it from `async void` commands (#110); the CLI still also treats `LODGroupCount == 0` after `Import()` as a failure, as a safety net.
- Needs `ContentTools.dll` in the same folder (`x64/<config>/`, so FBX SDK is needed to build it).

Exit codes: 0 ok, 1 import/save failed, 2 bad arguments, 3 input missing, 4 unsupported format/type mismatch, 5 bad settings, 6 output folder error, 7 `ContentTools.dll` not loadable, 10 unexpected.

## Build

`build.ps1 -Target editor` builds `DXForgeImport.csproj`, which builds the editor through the reference with the same properties (verified: an injected `CS8602` in the editor still fails `-WarningsAsErrors`).

## Test

`pwsh -STA -NoProfile -File DXForgeImport/Tests/import_cli_test.ps1 [-Configuration ReleaseEditor]` — needs `ContentTools.dll` and the FBX SDK sample `samples/ConvertScene/box.fbx`; also loads the CLI's `.asset` files with the editor's `Texture.Load`/`Geometry.Load` and compares them with the editor's own import path `ContentHelper.Import`. It also imports a broken FBX through `ContentHelper.Import` and checks that the `ImportingItem` ends `Failed`, no `.asset` is written and an error is logged (#110). CI runs only `-ArgumentsOnly` (argument/error cases, including exit code 7 since the runner has no `ContentTools.dll`, and the `AssetRegistry` check below).

- `AssetRegistry` (#137, no `ContentTools.dll` needed): a `Content` folder with a `.asset`, a `.fbm` folder image and a `.asset.bak` copy is registered through `AssetRegistry.Reset` and `OnContentModified`; only the `.asset` must be registered.
- Max mip count (#138, needs `ContentTools.dll`, so not run in CI): an 8192×4 PNG generated by the test is imported with `Compress=false`, `MipLevels=14`; with `DEBUG`, an assert in the CLI process would end it with `FailFast` (exit code -2146232797).
- While editor code runs in the test process, `Trace.Listeners` is replaced by a recorder, so a `Debug.Assert` in an editor built with `DEBUG` counts as a test failure instead of `FailFast`-ing pwsh. To check the asserts locally, build the editor with `dotnet build DXForgeImport/DXForgeImport.csproj -c DebugEditor -p:Platform=x64 "-p:DefineConstants=DEBUG%3BTRACE"` (without editing the `.csproj`) and run the test; rebuild normally afterwards.

- The test builds an embedded-texture FBX on the fly from the ASCII `box.fbx` (a `Video` object with base64 `Content` **plus** a `Video` entry in `Definitions` — without the latter, or without the `Properties70`/`Path`, the FBX SDK does not extract it to `.fbm`). The same FBX is then imported through the editor path (`ContentHelper.Import` with `ImportEmbeddedFiles` unset): `Project.Current` is set by reflection to a `Project` with only `Path` set, and the test pumps the dispatcher while `ConfigureImportSettings.Import` imports the texture on a worker thread.
- The partial-save test needs an FBX with several LOD groups. Neither the repo nor the SDK samples have one, so the test makes it from `box.fbx` with `DXForgeImport/Tests/make_multilod_fbx.py <box.fbx> <out.fbx>` (ASCII; two LOD groups with two LODs each; `-MultiLodFbxFile <fbx>` uses another file). Without either, the test is a SKIP. `ops_cli_test.ps1` uses the same FBX for `import-asset`.
- Pitfall: when comparing texture `.asset` bytes from pwsh, compare the *decompressed* payload — pwsh 7.6 runs on .NET 10, whose Deflate output differs byte-for-byte from .NET 8's (the CLI's and the editor's), so the compressed bytes and their SHA-256 hash differ even though the content is identical.
