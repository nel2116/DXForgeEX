# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

DXForgeEX is a from-scratch 3D game engine + WPF level editor, built by following the "Game Engine Series" (TheGameEngineers / Arash Khatami, `Primal` engine: https://github.com/TheGameEngineers/Primal) on YouTube. The codebase intentionally mirrors Primal's architecture: a platform-agnostic C++ engine core, a thin C-ABI DLL boundary, a C#/WPF editor that drives the engine through that DLL, and an offline content-tools pipeline (FBX/texture import) feeding a runtime content/asset system. When picking up unfinished work, treat Primal's commit history/video order as the reference roadmap for "what comes next."

Current implementation has PBR direct lighting (GGX/Smith/Schlick BRDF in `Shaders/BRDF.hlsli`) plus Image-Based Lighting (Primal Day 075, issues #35–#37). The IBL maps are baked offline by `ContentTools` (`EnvMapProcessing.*`/`EnvMapProcessing.hlsl`: equirectangular → cubemap, diffuse irradiance prefilter, specular prefilter with one mip per roughness step, BRDF integration LUT; exposed to the editor as `PrefilterDiffuseIBL`/`PrefilterSpecularIBL`/`ComputeBrdfIntegrationLut`). At run time they are bound through an `ambient` light (`graphics::light::ambient`, `ambient_params` in `Renderer.h`, one per light set, carried to shaders as `GlobalData.AmbientLight`); the material pixel shaders (`EngineTest/TestShader.hlsl`, the editor's `Resources/MaterialEditor/DefaultMaterialShaders.hlsl`) evaluate it, and `PostProcess.hlsl` draws the specular cubemap as the sky. `EngineTest` loads the maps from `x64/ibl/*.texture` and falls back to direct light only when they are missing. For "what comes next" on the renderer, follow Primal's history rather than assuming a fixed milestone.

## Solution layout

`DXForge.sln` has 4 solution configurations, all `x64`: `Debug`, `DebugEditor`, `Release`, `ReleaseEditor`. The `*Editor` configs build the engine as the `DXForgeEngineDLL` dynamic library for use by the editor; the plain `Debug`/`Release` configs build `EngineTest` as a standalone native executable that exercises the engine without the editor.

- **DXForgeEngine** (`StaticLibrary`) — the engine core. Linked into both `EngineTest` and `DXForgeEngineDLL`.
- **DXForgeEngineDLL** (`DynamicLibrary`) — thin C-ABI wrapper (`dllmain.cpp`, `EngineAPI.cpp`, `EntityAPI.cpp`) exposing `DXForgeEngine` to the C# editor via `DllWrappers`; also hosts `ShaderCompilation.cpp` (DXC), which `EngineTest` compiles in as well (Primal Day 076).
- **EngineTest** (`Application`) — standalone native test harness (`Main.cpp`, `TestRenderer.cpp`, `Lights.cpp`, `Scripts.cpp`, `RenderItem.cpp`) for driving/visually testing the engine without the editor or a game project. Interactive: requires a window and a GPU, and gates on keyboard input — not suitable for CLI/CI.
- **EngineUnitTests** (`Application`) — headless automated test runner (Debug/Release only, no Editor configs). Links `DXForgeEngine` but needs no window or GPU device; covers pure-logic modules only (currently `Common/Id.h`, `Utilities/FreeList.h`). Uses a dependency-free micro test framework (`MicroTest.h`: `DXFORGE_TEST_CASE`/`CHECK`/`REQUIRE`) rather than a vendored library. Exits non-zero on any failed check; `--json` prints a machine-readable summary. This is the first piece of a longer-term "AI/CLI-friendly engine" direction (see root `README.md`) — favor extending this runner (new `Tests_*.cpp` files, or eventually command-line-driven headless engine operation) over reviving `EngineTest` for anything that needs to run unattended.
- **ContentTools** (`DynamicLibrary`) — offline asset pipeline: FBX import (`FbxImporter.*`, Autodesk FBX SDK), texture import (`TextureImpoter.cpp`, DirectXTex), procedural primitive meshes (`PrimitiveMesh.*`), tangent generation (MikkTSpace), normal-map detection. Consumed by the editor, not linked into the runtime engine.
- **DXForgeEditor** (C#/.NET WPF, `ConfigurationType` mapped to the Editor configs) — project browser/creation, scene & game-entity editing (undo/redo commands), content browser, texture/geometry editors, Visual Studio automation for generating and building per-game-project C++ solutions (`ProjectTemplates/*`, `GameDev/VisualStudio.cs`).
- **DXForgeImport** (C#/.NET console app, `DebugEditor`/`ReleaseEditor` only, like the editor; issue #10) — headless asset importer: `DXForgeImport --input <file> --output <folder> [--type auto|geometry|texture] [--settings import.json] [--set Name=Value] [--json]` writes the same `.asset` files as the editor's drag-and-drop import (FBX → geometry, images → texture; IBL prefiltering and primitive meshes are not exposed yet). It does **not** reimplement the `.asset` format: it `ProjectReference`s `DXForgeEditor` (`InternalsVisibleTo("DXForgeImport")`) and calls the editor's own `Content` code (`ContentHelper.CreateAsset`/`GetAssetName`/`GetAssetFullPath`, `Asset.Import`/`Save`), so the format stays implemented in one place. The editor's dependencies on an open project are swapped through `Content/ContentImportEnvironment.cs` (`TempFolder` for the FBX temp copy, `ImportEmbeddedFiles` for `.fbm` embedded textures; both `null` in the editor = unchanged behavior) and `Logger.MessageLogged` (synchronous log event → stderr/JSON). WPF is still needed (logger dispatcher, geometry icon rendering via `GeometryView`): the CLI creates a plain `Application` on its STA main thread, merges only `DXForgeEditor;component/Dictionaries/EditorColors.xaml` (the editor's `App` is not used: its `App.xaml` dictionaries use `pack://application:,,,/...`, which resolves against the *entry* assembly, and it has `StartupUri`), never calls `Run()`, and never shuts the dispatcher down (`Logger.Log` is `async void` and awaits `BeginInvoke`; a stopped dispatcher would throw out of it). No window, project or GPU window is needed (texture compression creates a windowless D3D11 device and falls back to the CPU). Embedded FBX textures are copied from the temp `.fbm` into `<output>/<fbx asset name>.fbm/` before importing, so the texture `.asset`'s `Sources` (used by the editor's reimport) does not point into the deleted temp folder. A geometry save is checked against `Geometry.LODGroupCount` and against errors logged during `Save()`, because `Geometry.Save()` catches its own exception and returns only the files written so far (partial save → exit 1, written files stay in `files`). The test builds an embedded-texture FBX on the fly from the ASCII `box.fbx` (a `Video` object with base64 `Content` **plus** a `Video` entry in `Definitions` — without the latter, or without the `Properties70`/`Path`, the FBX SDK does not extract it to `.fbm`); `-MultiLodFbxFile <fbx>` enables the partial-save test (no multi-LOD-group FBX in the repo or the SDK samples). Needs `ContentTools.dll` in the same folder (`x64/<config>/`, so FBX SDK is needed to build it). Exit codes: 0 ok, 1 import/save failed, 2 bad arguments, 3 input missing, 4 unsupported format/type mismatch, 5 bad settings, 6 output folder error, 7 `ContentTools.dll` not loadable, 10 unexpected. `build.ps1 -Target editor` builds `DXForgeImport.csproj`, which builds the editor through the reference with the same properties (verified: an injected `CS8602` in the editor still fails `-WarningsAsErrors`). Test: `pwsh -STA -NoProfile -File DXForgeImport/Tests/import_cli_test.ps1 [-Configuration ReleaseEditor]` (needs `ContentTools.dll` and the FBX SDK sample `samples/ConvertScene/box.fbx`; also loads the CLI's `.asset` files with the editor's `Texture.Load`/`Geometry.Load` and compares them with the editor's own import path `ContentHelper.Import`). CI runs only `-ArgumentsOnly` (argument/error cases, including exit code 7 since the runner has no `ContentTools.dll`). Pitfall: when comparing texture `.asset` bytes from pwsh, compare the *decompressed* payload — pwsh 7.6 runs on .NET 10, whose Deflate output differs byte-for-byte from .NET 8's (the CLI's and the editor's), so the compressed bytes and their SHA-256 hash differ even though the content is identical.

Build via Visual Studio 2022 (`PlatformToolset v143`, open `DXForge.sln`) or via the CLI: root `build.ps1` wraps MSBuild (native) and `dotnet build` (editor) and can run `EngineUnitTests` afterwards — see `README.md` for the parameter list. It summarizes build output by default (see Keeping sessions cheap below). **Always build native projects through `DXForge.sln`** (directly invoking a `.vcxproj` makes `$(SolutionDir)` fall back to the project's own directory, breaking the `AdditionalIncludeDirectories` paths — `build.ps1` already does this correctly via `/t:<ProjectName>`). `GetDXC.ps1` fetches the DirectX Shader Compiler package used for shader compilation (`packages/DirectXShaderCompiler`); it downloads the *latest* DXC release whenever `packages/DirectXShaderCompiler` is empty, so CI caches that directory to avoid GitHub API rate limits. Only `EngineTest` (runtime shader compilation) uses that GitHub DXC, so `Restore.ps1` fetches it only when `EngineTest` is part of the build (`Debug`/`Release` with no `-Project`, or `-Project EngineTest`); `-Project EngineUnitTests` and the `*Editor` configs build offline without it (issue #61). The editor-side shader compilation (`DXForgeEngineDLL`'s `CompileShader`, Primal Day 076, issue #29) uses a separate, version-pinned NuGet package `Microsoft.Direct3D.DXC` (`DXForgeEngineDLL/packages.config`, restored with the other `*Editor` NuGet packages); its targets copy `dxcompiler.dll`/`dxil.dll` next to `DXForgeEngineDLL.dll` (= the editor's output folder). `ShaderCompilation.cpp` (shared with `EngineTest`) loads DXC at run time with `LoadLibraryExW` from its own module's folder instead of linking `dxcompiler.lib`, so a missing DXC only fails the compilation (logged) instead of making `DXForgeEngineDLL.dll` unloadable. Headless checks: `python DXForgeEngineDLL/Tests/shader_compilation_test.py` (C ABI via ctypes) and `pwsh -STA -File DXForgeEngineDLL/Tests/editor_shader_compilation_test.ps1` (the editor's own `DllWrappers` via reflection, including the Logger output). `EngineUnitTests` covers only pure-logic modules; rendering/GPU code (`Graphics/Direct3D12/*`) still has to be verified by running `EngineTest` or the editor and visually inspecting the render output.

**New C++ source files must be saved with a UTF-8 BOM.** Every existing file in this repo starts with a Japanese header comment (see below); without a BOM, MSVC misdetects the file as the local codepage (Shift-JIS) instead of UTF-8 and corrupts the token stream, producing unrelated-looking cascading compile errors. If a new file produces confusing errors at/after its first Japanese comment, check for a missing BOM first.

## Quality gates

- **CI** (`.github/workflows/ci.yml`): on push to `main`/`develop` and on every PR — native build + `EngineUnitTests` in both `Debug` and `Release` (Release defines `NDEBUG`, which compiles out the `assert`s that `free_list`/`Id` rely on for self-checks, so both configs are verified), plus a `dotnet build` of the editor. `ContentTools` is deliberately out of CI scope: it needs the Autodesk FBX SDK, which runners don't have, and the `Debug`/`Release` solution configs don't build it anyway. The SDK location is the `FbxSdkDir` property in `ContentTools/FbxSdk.props` (defaults to the standard 2020.3.7 install path; override via env var or `/p:FbxSdkDir=`; a missing SDK fails early with a clear error). Note `/p:` global properties are immutable inside the project, so normalize into a *different* property name rather than reassigning `FbxSdkDir`. The old hardcoded `MSVC\14.42.34433\atlmfc` paths were removed: ATL (`atlsafe.h` in `Script.cpp`/`EngineAPI.cpp`) resolves through the default `$(IncludePath)`/`$(LibraryPath)` as long as the VS "C++ ATL" component is installed.
- **Warnings as errors**: the native side is currently at **zero warnings** in both configs — keep it that way. Local builds stay lenient; CI passes `-WarningsAsErrors`. Run `./build.ps1 -Target native -WarningsAsErrors` to check locally before pushing. **`/p:TreatWarningAsError=true` does not work for C++ projects** (a global property never reaches `ClCompile` item metadata, so the compiler still gets `/WX-`); the gate is implemented as an `ItemDefinitionGroup` in the root `Directory.Build.props`, switched on by `/p:DXForgeWarningsAsErrors=true`. Verified empirically: with the switch the compile line carries `/WX` and an injected `C4189` fails the build. The **editor is also at zero warnings** (issue #9: 272 unique nullable warnings fixed with `<Nullable>enable</Nullable>` kept); the same `-WarningsAsErrors` switch passes `-p:TreatWarningsAsErrors=true --no-incremental` to `dotnet build` (full rebuild, because an up-to-date incremental build re-emits no warnings), and CI uses it. Verified: an injected `CS8602` fails the build. When fixing nullable warnings, prefer honest `?` annotations and `Debug.Assert` over `!`, and never turn a swallowed failure into a thrown exception on a path reached from `async void` commands or `OpenProjectView` — nothing catches it there and the editor crashes.
- **`.editorconfig`**: encodes the measured conventions — `.c/.cpp/.h/.hpp` are UTF-8 BOM + tabs (113/113 files), `.cs`/`.xaml` are UTF-8 BOM + 4 spaces (71/71 files). `.hlsl`/`.hlsli` are UTF-8 BOM + 4 spaces (the 8 engine shaders with Japanese comments were converted from Shift-JIS in issue #7), **except** the fxc-compiled ones under `ContentTools/` and `DXForgeEditor/`, which must stay BOM-less (`charset = utf-8`). Both halves were verified empirically: the engine shaders need the BOM for the same reason C++ does, because `Shaders/SharedTypes.h` `#include`s `CommonTypes.hlsli` into the C++ build (BOM-less UTF-8 there gives `C4819` → `/WX` failure), and DXC accepts either; fxc (`ContentTools/CompileShaders.cmd`, the WPF pixel shader, Visual Studio's HLSL build for SM 5.x) rejects a BOM with `error X3000: Illegal character in shader file`, directly or through `#include`.
- **Japanese text must never appear in a narrow string literal.** CI runners are not Japanese-locale: their system code page is 1252, and MSVC converts narrow literals to the execution charset, so Japanese characters there produce one `C4566` per character and fail the `/WX` build (this is real: it is locale-dependent string data, not CI noise). Comments are fine — only literals matter. Use the wide API instead (`OutputDebugStringW(L"...")`, as `D3D12Core.cpp` now does); wide literals are UTF-16 and code-page independent. A full scan found exactly one such literal in 113 C++ files, so this is rare — but note the symptom is Debug-only when the code sits inside `#if _DEBUG`.
- **Do not silence a warning that points at a real defect.** The two `C4100` warnings that existed before the gate turned out to mark a genuine bug: `transform::set_orientation` is an empty function body, yet it is reachable from the public API (`entity.set_orientation()` → `entity_script::set_orientation` → the orientation flag branch in `transform::update`), so the value is silently dropped. This has since been resolved (issue #4) by porting Primal Day 086 (commit `db1c19d`): `set_orientation`/`orientation()` and the `orientation` component flag were removed, and each transform now stores a local frame (`right()`/`up()`/`front()`/`local_frame()`) derived from the rotation quaternion, so a direction is changed by setting a rotation instead.
- **Cross-model review with Codex** (issue #56): before a PR is proposed for merge, run `./CodexReview.ps1 -Pr <N> -Post`. It checks out the PR head into a throwaway worktree under `%TEMP%`, runs `codex review` against the tip of the PR's base branch (both fetched from the repo `gh` resolves into script-private `refs/codex-review/<N>-<runId>/*` refs, deleted afterwards, so `origin` layout does not matter), and posts the result as a PR comment (omit `-Post` to only print it). The point is a reviewer that does not share the author's blind spots: on its first run it found a P2 in PR #52 that both the implementing worker and the coordinator's diff read had missed (the editor never calls `script::update()`, so the `begin_play` pending queue grows on every game-DLL reload). In orchestrated work the **coordinator** runs it (never the implementing worker), forwards each finding to that worker, and the worker either fixes it or replies on the PR with why not; re-run the review after fixes. Merging is automated (see the next item); the coordinator decides *when* a PR is ready, not the merge itself. Pitfalls, both verified: (1) on Windows, Codex's sandbox is disabled by default, and then even a read-only review has every shell command rejected as `blocked by policy` — Codex then reports it could not read the diff instead of reviewing; the script passes `-c windows.sandbox="unelevated"` per call (the global `~/.codex/config.toml` is untouched) and fails loudly if `blocked by policy` still appears. (2) `codex review` rejects `--base` combined with custom instructions, so the diff range is named inside the prompt. Expect 1–2 minutes per PR; it neither builds nor tests, so it complements CI rather than replacing it. Already-merged PRs work too (issue #58): the base tip already contains the PR, so the script instead diffs the merge commit's two parents and has Codex label each finding "still present" or "fixed since" against the current base tip — merge-commit merges only (every PR so far). Several reviews can run in parallel (fetch uses `--no-write-fetch-head` because the shared `FETCH_HEAD` otherwise races).
- **Auto-merge into `develop`**: branch protection on `develop` requires five checks — the three CI jobs, `No hold label` (`.github/workflows/pr-automation.yml`), and the commit status `codex-review` — with admins included, so nothing (not even an admin `gh pr merge`) lands without them. The coordinator runs `./CodexReview.ps1 -Pr <N> -Post -SetStatus` **only once the PR's completion criteria are met** (CI green, GUI checks done, earlier findings resolved): the verdict is read from `codex review`'s own output format — every finding is rendered as a `- [P0..P3] title — file:lines` line under `Full review comments:` — because `codex review` ignores custom instructions about output format (a requested `VERDICT:` line never appeared; found by Codex itself on PR #96). Any finding, regardless of severity → `codex-review` = failure. Success (on the reviewed SHA, followed by `gh pr merge --auto --merge`) needs positive evidence too: no finding line **and** the phrase 「問題は見つかりませんでした」, which the prompt asks for and which free-text summaries do honor; anything else (e.g. `Reviewer failed to output a response.`) → failure, so an incomplete review never passes. If a Codex upgrade changes that rendering, a review with findings would read as PASS, so re-check the format after upgrading `codex-cli` (verified on 0.163.0). `-SetStatus` refuses (before reviewing) unless the base branch's protection requires both `codex-review` and `No hold label`. A status belongs to a commit, so pushing a fix drops it and the PR waits for a fresh review — no unreviewed fix can merge. A human stops a merge by adding the `hold` label (also works after `codex-review` passed); removing it re-runs the gate. GitHub deletes the head branch on merge (`delete_branch_on_merge`), and the `close-issues` job closes `Closes #NN` issues, which GitHub itself only does for PRs into the default branch (`main`). It runs on `push` to `develop` and looks up the merged PR from the pushed commits (`commits/<sha>/pulls`), because both obvious triggers fail: a fork PR's `pull_request` token is read-only, and `pull_request_target` always runs the *default branch's* (`main`'s) copy of the workflow, so a workflow that exists only on `develop` never fires (both found by Codex on PR #96). `-SetStatus` also re-reads the PR's base before scheduling the merge, since a base changed mid-review would bypass the protection check. Local cleanup is `./CleanupMerged.ps1` (`-DryRun` to preview): it removes a worktree/local branch only if its PR is merged, its tip is contained in `origin/develop`, and the worktree has no changes or untracked files (so a freshly created, still-empty worker worktree is never touched), then fast-forwards the root `develop`. Run it without being asked after merges and in the pre-flight check of an orchestration. Pitfall: `gh pr merge --auto` merges *immediately* when no required check is pending, so never use it on a branch without this protection.

## Keeping sessions cheap

Build-tool output is the dominant token cost in this repo. Measured on a full compile: the native
MSBuild log is ~7,400 characters at default verbosity, and `dotnet build` of the editor is
was **~132,000 characters** while it had 588 nullable warnings (272 unique, printed twice because of the
WPF temp project; fixed in issue #9 — the editor's raw minimal-verbosity log is now ~470 characters).
`build.ps1` still summarizes by default — errors verbatim, warnings folded into per-code counts — so a
regression cannot flood the session again.

- **Never pass `-DetailedLog` unless actually diagnosing a build failure**, and never re-run a build
  just to see its full log when the summary already named the error.
- **Scope the build**: `-Target native -Project EngineUnitTests` for the test loop. Building the
  whole solution, or `-Target all`, costs much more and is rarely needed.
- **Reading CI logs**: `gh run view <id> --json conclusion,jobs` first. `--log-failed` dumps the raw
  log (the C4566 failure was 43 near-identical lines); only reach for it when the job summary is not
  enough, and pipe it through `tail`/`grep`.
- Don't re-read a file right after writing it, and prefer `sed -n '<range>p'` over reading whole
  files when a specific function is what matters.
- **Write edit scripts to a file, don't inline them.** A quoted heredoc passed to `python -`/`pwsh -Command`
  loses backslashes on the way in: Windows paths break (`swhere` becomes a vertical tab), `
` becomes a
  real newline so patterns stop matching, and regex character classes like `[^"\]` fail to compile. Write the
  script (or the replacement text) into the scratchpad directory with a quoted heredoc and run it by path, or
  match on a backslash-free substring. Each mangled attempt is a wasted round trip.
- `python3` on this machine is the Windows Store stub and silently does nothing — use `python`.
- Verify with the fast path: `EngineUnitTests` is seconds; a full `Debug`+`Release` sweep is minutes
  and only needed before pushing.

## Engine architecture

- **Platform abstraction**: `Platform/Platform.h` + `PlatformWin32.cpp` wrap OS window handling behind a platform-independent interface; `Window.h` is the cross-platform window handle type.
- **Graphics abstraction**: `Graphics/GraphicsPlatformInterface.h` defines a `platform_interface` struct of function pointers (surface, light, camera, submesh/texture/material, render) that each graphics backend fills in. `Graphics/Renderer.cpp` selects a backend (`graphics_platform::direct3d12/vulkan/opengl`) and forwards calls to it. **Only Direct3D12 (`Graphics/Direct3D12/`) is actually implemented**; the Vulkan/OpenGL folders exist as stubs for future backends — do not assume they work.
- **D3D12 backend** (`Graphics/Direct3D12/`): `D3D12Core` (device/queues/sync), `D3D12Surface` (swap chain per window), `D3D12Resource`/`D3D12Helpers` (descriptor heaps, deferred resource release, free-list-backed id allocation), `D3D12Upload` (copy-queue GPU uploader), `D3D12Content` (GPU-side submesh/texture/material storage), `D3D12GPass` (depth prepass + geometry/lighting pass, draw-indirect), `D3D12Light`/`D3D12LightCulling` (tiled light culling via compute shader — frustum grid build + culling, see `Shaders/GridFrustums.hlsl`/`CullLights.hlsl`), `D3D12PostProcess` (fullscreen post pass). Engine HLSL shaders live under `Graphics/Direct3D12/Shaders/` and are precompiled offline into a `shaders.bin` blob referenced by `Renderer.cpp`'s `engine_shader_paths`.
- **ECS**: `Components/Entity.*` is the game-entity container; `Transform`, `Script`, `Geometry` are components attached via generational IDs (`Common/Id.h`). `EngineAPI/*.h` are the public structs/handles (camera, light, game entity, transform/script/geometry component, input) exposed across the DLL boundary — these mirror internal types but are kept ABI-stable for the editor and game code.
- **Content pipeline (runtime side)**: `Content/ContentToEngine.*` converts compiled asset blobs (meshes, textures, materials, shaders — see `asset_type`/`texture_flags` enums) into GPU resources via the active graphics backend; `Content/ContentLoader.*` handles loading the game DLL and engine shader blob (editor/dev builds only, guarded by `!defined(SHIPPING)`).
- **Content pipeline (offline side, `ContentTools`)**: separate from the runtime; produces the asset files `ContentToEngine` consumes. FBX scenes are traversed/packed into submesh+LOD hierarchies; textures go through DirectXTex import/compression; tangents are generated with MikkTSpace for normal mapping.
- **Game code**: each game project gets its own generated Visual Studio solution/project (from `DXForgeEditor/ProjectTemplates/*`), built via editor-driven VS automation (`GameDev/VisualStudio.cs`) and loaded as a DLL at runtime (`ContentLoader::load_game`).

## Editor architecture (DXForgeEditor, C#/WPF)

- `GameProject/` — project creation/open (`NewProject.cs`, `OpenProject.cs`), the `Project`/`Scene` models, and the undo/redo command system backing entity/component edits.
- `Components/` — editor-side mirrors of engine components (transform, script, geometry) with multi-selection support, bound to WPF views.
- `DllWrappers/` — P/Invoke boundary calling into `DXForgeEngineDLL`.
- `Content/ContentBrowser/`, `Editors/TextureEditor/`, `Editors/GeometryEditor/`, `Editors/WorldEditor/` — asset browsing and per-asset-type editors (texture detail/RGBA channel view, geometry/primitive preview, scene/world viewport with its own render surface).
- `Utilities/RenderSurface/` — hosts a Win32 D3D12 render surface inside WPF (HwndHost-style interop) for viewport rendering.

## Conventions to follow when adding/editing C++ files

Existing engine/editor C++ source files begin with a standardized Japanese header comment block giving the filename, creation date, author, a one-line summary, and an update history log (date + change description per entry), e.g.:

```cpp
// _/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/
// [FileName.cpp]
// 作成日 : YYYY/MM/DD
// 作成者 : 田中ミノル
// 概要
// 　一行概要
// 更新履歴
// YYYY/MM/DD 変更内容
// _/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/_/
```

When modifying an existing file this way, append a new dated line to the 更新履歴 (update history) rather than rewriting prior entries. New files should follow the same header format for consistency, append-only history. All engine code lives under the `dxforge` namespace (sub-namespaced per module, e.g. `dxforge::graphics`, `dxforge::content`).
